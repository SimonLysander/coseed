# CoSeed 业务设计

状态：第一版业务设计；数据库及内部共同保存／查询服务已实现，项目管理、业务内容和回顾的页面／MCP 流程待接入。实际边界见 [Architecture](../../ARCHITECTURE.md)。

## 1. 产品是什么

CoSeed 是供开发者与 Coding Agent 协作使用的项目认知工作台。它帮助人持续理解项目的需求、业务和实现设计，保留关键变化及其依据，在 Agent 快速编码时仍能参与架构和策略判断。

主要用户是借助 Coding Agent 开发项目的人。开发者通过页面阅读、定位和修正内容，所用 Agent 在协作过程中通过 MCP 查询内容，并在用户明确发起回顾后整理和更新。两种入口围绕同一项目、同一份内容工作。

### 已确定的方向

- 项目综述按“产品是什么、核心概念、使用示例”组织。
- 核心概念使用关系图和词条；种属、组成、业务关联有明确含义，词条缩进只表示种属。
- 使用示例开头先用自然 Markdown 说明参与者、当前情况与共同前提，以及整组例子要说明什么；每个小标题下放对应的用例图，再接本节正文。某一节独有的前提写在该节正文中。
- 项目综述页右侧提供阅读目录；该页图形固定适应画布。
- 业务设计以图为主；从顶层业务模块进入模块内部理解实现。技术方案依附于相关节点或范围。
- 需求的演变应与项目当前表述相互关联。
- 需求推进主要通过用户明确触发的阶段回顾补齐；不按每个工具调用或每轮对话自动生成记录。
- 记录本身可以被修改，需要区分修正旧记录与新增真实进展。
- 每一次更正必须记录具体来源、修改前后、操作者和修改时间，适用于所有可维护内容及所有写入入口。
- CoSeed 提供可部署的服务，不默认公开项目供他人浏览或提交；远程访问的具体认证与授权方式待设计。
- 内容隔离单位确定为项目：同一服务实例可以管理多个项目，综述、需求、设计、回顾、来源引用及修订历史均归属具体项目；默认不允许跨项目读取、更新或关联。
- Agent 使用产品已有的 MCP 客户端能力直接连接 CoSeed；不要求安装独立本地连接器，不管理 Agent 执行器。业务仓库不必包含 CoSeed 资料，创建项目也不强制登记业务仓库地址。
- 项目资料及其历史由数据库保存。Agent 初始化时经 MCP 拉取完整当前资料到本地读取副本，日常可直接读取和搜索；正式修改经 MCP 提交并校验，成功后刷新副本。不使用资料 Git 仓库，具体存储和同步边界见 [ADR 0003](../adr/0003-database-and-agent-cache.md)，尚未实现。

下文区分已确认规则和首版建议；数据库约束及内部服务见 [存储实现](../database/storage-implementation.md)，页面与工具行为不能据此视为已完成。

### 项目隔离规则

- 每次读取、编辑或回顾都要明确目标项目；页面切换与 MCP 客户端操作使用各自明确的项目上下文，不能仅依赖一个全局“当前项目”来猜测写入对象。
- 校验所有目标对象、关联内容和来源引用属于该项目；对象标识已知不代表可以跨项目访问。更正及其历史沿用被更正内容的项目归属。
- 回顾一次只整理一个项目。切换到其他项目后，已有回顾不改变目标归属，也不把结果写进新打开的项目。
- 项目隔离不等于公开共享，也不替代访问授权。项目是服务中的内容隔离边界，不据此增加租户、组织或跨用户协作体系；远程访问仍需单独明确项目授权。

内部存储已按项目标识校验全部对象和来源引用；入口授权及页面／MCP 项目上下文仍待接入。

## 2. 核心概念

### 项目

CoSeed 中被说明和推进的软件项目，关联其代码仓库，并组织属于它的综述、需求、设计和回顾。它是内容归属边界，不等于一次聊天或一次 Agent 执行。CoSeed 自身也可以成为被管理的项目。

### 项目综述

项目当前整体需求和业务认识的连贯表述，包括产品是什么、核心概念和使用示例。它帮助新读者理解项目当前要做什么，不是把所有历史讨论按时间拼接起来。需求变化影响整体认识时，应同步修订综述。

核心概念词条、概念关系、使用示例及其用例图属于综述的内部内容，不在第一版中各自建立独立管理中心。概念不是数据库表，用例也不是内部函数调用。

### 需求

一个相对独立、可以讨论范围和判断完成情况的用户目标。需求需要说明为谁解决什么问题、做到哪里、怎样判断结果。它可以被多次讨论，影响多个业务模块，并拥有多条推进记录，不随聊天轮次重新建立。

### 推进记录

围绕一个需求形成的一条有意义的结论或结果，例如澄清范围、确定方案、改变决定、完成并验证一部分能力。正文采用自由 Markdown，通常约 100～200 字，详实凝练；不强制句式或固定小标题。

记录至少应能识别所属需求、标题、正文、实际发生时间和来源。系统另行保存创建、修改时间及操作者；同一记录的首版及每次修订各自保留保存时间、修改者和来源，不能只留下会被覆盖的最后修改时间。实际发生时间无法核实就保留未知，不使用保存时间伪装成讨论发生时间。

### 业务模块

项目中承担一组内聚业务职责的功能边界，是顶层设计的主要组成部分。模块说明负责什么、与哪些模块有功能依赖，并可进入内部设计。需求说明用户目标，模块说明职责划分，两者分别维护并建立关联。

### 设计图

针对一个明确对象或问题的设计视图，使用节点、连线、边界及说明表达业务或实现结构。多张图可以引用同一个模块或对象，图上的坐标和布局不决定业务对象身份。

第一版重点维护业务全景及模块内部设计。图上能清楚表达的关系放在图中，文字补充必要解释，避免外围重复罗列图中已有内容。

### 技术方案

为一个节点或一组节点采用的关键实现策略，例如状态机、设计模式、事务边界、幂等和失败恢复。它说明采用什么机制以及解决什么问题，依附于对应设计范围，不另建独立的“项目技术设计”入口。

### 回顾

用户明确发起的一次整理工作，对指定来源范围内的讨论和仓库变化进行核对，补齐或修正需求、推进记录及当前综述和设计。一次回顾可以涉及多个需求；同一需求可以出现在多次回顾中。

回顾不是一次产品版本，也不是需求本身。只有结论或结果值得保留时，才形成推进记录，不为让时间线显得完整而记录所有交互。

### 来源

支撑内容的原始材料，例如用户明确表达的对话片段、代码位置、提交差异和验证结果。来源应能定位到对应材料，并说明材料支持什么结论。仅有摘要或 Agent 的判断，不等于已保存原始证据。

对话可以支持用户意图，代码可以支持实现事实，测试可以支持已验证行为；三者不能互相冒充。

### 修订

对同一条内容所作的修改及其历史。修正描述、补充遗漏或纠正误记时，应保留原记录身份，同时留下修改前后内容、修改者、修改时间和具体来源。该规则覆盖综述、概念、需求、推进记录、设计和技术方案，不只覆盖推进记录。后来真正发生的新进展，应新增推进记录，不覆盖过去当时成立的结论。

## 3. 业务关系

| 概念之间                    | 业务含义                     | 边界                                             |
| --------------------------- | ---------------------------- | ------------------------------------------------ |
| 项目 → 项目综述             | 项目包含当前整体表述         | 历史变化通过修订追溯，不把历次综述当成不同项目   |
| 项目 → 需求                 | 项目拥有若干需求             | 需求只归属于一个项目                             |
| 需求 → 推进记录             | 一个需求积累多条记录         | 每条记录有且只有一个主需求；可引用其他相关对象   |
| 项目 → 业务模块             | 项目按业务职责拆分           | 模块与需求分别建模                               |
| 需求 → 业务模块             | 实现需求涉及哪些模块         | 两边都可以关联多个对象，不强行一一对应           |
| 设计图 → 业务模块、内部对象 | 图表达对象及其关系           | 同一对象可被多张图引用，释义和身份保持一致       |
| 技术方案 → 设计范围         | 方案解释一个节点或一组节点   | 明确机制与所解决的问题，不要求再下钻到类和函数   |
| 项目 → 回顾                 | 项目保留整理工作的范围与结果 | 一次回顾针对一个项目，可影响多个需求             |
| 回顾 → 来源                 | 回顾核对选定的讨论及仓库材料 | 回顾范围必须明确；不同对话分别标识范围           |
| 回顾 → 内容                 | 回顾新增或修订项目内容       | 不要求每次都修改所有页面                         |
| 内容 → 来源                 | 内容具有可核对的依据         | 一个来源可以支持多项内容，一项内容可以有多个来源 |
| 内容 → 修订                 | 内容的修改留下历史           | 修改时间与业务实际发生时间分别保存               |

“内容”在此表中是综述、需求、推进记录、设计与方案等可维护材料的统称，不据此预设一张通用内容表。

## 4. 第一版管理什么

| 业务职责 | 用户可做的事                                       | 应维护的边界                             |
| -------- | -------------------------------------------------- | ---------------------------------------- |
| 项目管理 | 建立项目、关联仓库、选择当前项目                   | 切换项目后，读取和更新都必须归属所选项目 |
| 综述维护 | 阅读并修正产品表述、概念和示例                     | 始终表达项目当前认识，保留重要修订       |
| 需求推进 | 建立需求、阅读时间线、修正记录、补充来源           | 按用户目标归并需求，按结论或结果划分记录 |
| 设计维护 | 管理业务模块、设计图、关系和技术说明               | 保持对象引用及职责边界一致               |
| 回顾整理 | 选择讨论范围、核对仓库变化、补齐内容、查看整理结果 | 处理已明确的结论，区分事实、提议和未知   |

回顾整理负责识别来源范围、归并结果并组织相关更新；综述、需求和设计各自维护自身内容规则。回顾不因此成为另一套内容，也不复制这些职责的规则。来源和修订为共同能力，通过引用复用，不为每个页面重复保存同一原始材料。

页面是人的操作入口，MCP 是 Agent 的操作入口；两者使用同一套业务规则。保存不能仅因来自 Agent 就绕过归属、引用和修改冲突检查。

第一版聚焦本地开发者使用。团队成员权限、云端协同和组织管理尚未列入已确定的首版范围。

## 5. 需求和记录怎样划界

### 需求边界

满足同一个用户目标、共享主要范围和完成标准的讨论，持续归入同一需求。新增细节、修改展示形式、补充约束，不自动建立新需求。

当目标可以独立使用和验收、推进与否可以单独决定时，才建立另一个需求。仅因换了聊天、过了一下午或改了一次版本，不拆需求。

### 记录边界

一条记录表达一项可以独立理解的结论或结果。为理解同一结论所必需的原因、约束和影响可以写在一起；无关结果拆开。

例如“每个示例小节配图并保留正文”是一条设计结论；“已完成实现并验证定位和图文对应”是之后的一条结果。安装依赖、读取文件、点击测试等过程不逐条记录。

### 修改和新增

- 当时没有说清楚、摘要误记、来源缺失：修订原记录，并保留历史。
- 后来形成新决定、推翻旧决定或取得新结果：新增记录，引用原结论并说明变化。
- 用户手动修正过内容，后到的回顾不能静默覆盖；发生冲突时保留现有内容并明确指出冲突。

### 每次更正必须能够回答的问题

| 信息     | 要求                                                                                 |
| -------- | ------------------------------------------------------------------------------------ |
| 改了什么 | 关联被修改的对象及具体部分，保留修改前后内容；不能只记录“项目已更新”                 |
| 谁改的   | 记录实际执行者及入口；由 Agent 代为整理时，区分执行者与原决定提出者                  |
| 何时修改 | 保存系统实际修改时间；来源事件的发生时间另外保存，无法核实时保留未知                 |
| 来自哪里 | 定位支撑本次更正的具体对话、人工编辑、代码或验证材料，不仅注明“来自 Codex”或某次回顾 |

对话来源需要保留支撑结论的原始片段，并记录可用的会话及消息定位信息。尚未获得平台稳定标识时，可以使用本地保存的原始材料标识和片段位置，但不能伪造平台消息编号。代码依据应能识别相应版本和位置，验证依据应保留实际结果及其验证对象，避免以后只看到已变化的文件或过期结果。

用户直接在页面更正时，该次人工编辑本身就是来源，保存原始修改及操作者，不强迫用户编造另一段外部对话。Agent 更正则要关联它据以更新的具体材料，不能用“AI 整理”代替出处。同一次回顾更新多处内容时，各项更正分别关联实际依据，可以复用同一来源，但不能只笼统挂上整段聊天。

来源材料与更正历史保留原貌。需要纠正先前来源解释或撤销错误更正时，再追加修订说明，不覆盖旧材料或移除旧更正。当前页面仍显示最新内容，历史入口负责追溯每一次变化。

正式保存更正时，当前内容、修订历史与来源引用必须一起保存。无法提供可核对来源的 Agent 更正应保持待补充，不能覆盖当前内容。更正历史与需求推进时间线分别承担职责：修正措辞也保留更正历史，但不因此制造一条新的业务进展。

需求状态确定为“设计中、方案已定、待验收、已完成、暂缓、取消”。设计中包含需求理解、UI／交互及技术方案等必要设计；方案已定表示本需求已有足以支撑实现的方案。状态不设不可逆终态，可回退、恢复和跳转；每次真实变化保留需求版本、原因、来源与系统记录时间。正文修订但状态未变，不冒充一次状态变化；不根据 Agent 完成编码或一次回顾成功自动宣布需求完成。具体值和字段见[需求模型](../database/requirements-design.md)，各类历史的共同要求见[历史规范](../database/history-design.md)。

真实业务状态变化关联支撑它的一条或多条推进记录，并固定到具体版本；相关记录、状态版本和依据一起保存。首次建立需求直接使用原始来源，纠正误记可使用更正依据，不必伪造新的业务进展。后续修订记录不覆盖旧状态变化所依据的历史版本。

## 6. 一次回顾怎样进行

1. 用户明确发起回顾，选择项目并界定对话来源和起止范围；已有成功回顾时，可继续处理其后的未整理范围。
2. 外部 Agent 读取其可访问的原始讨论和相关仓库变化，经 MCP 检查项目版本，拉取或刷新本地完整当前资料后读取已有需求、记录及设计；不具备本地文件能力时直接通过 MCP 读取。CoSeed 不负责读取特定客户端的私有会话存储。
3. 根据目标归并已有需求，必要时建立独立需求；识别新增结论、实际结果与旧记录需要修正的部分。
4. 明确结论整理为推进记录；事实、设计提议和待确认问题分别标明，不把推断写成已确定需求。
5. 判断这些变化是否影响当前综述、概念或设计；有影响才同步修订，并保持相关对象引用有效。
6. 保存本次相关更新和修订，记录实际处理范围，并向用户说明更新了哪些内容、还缺什么材料。

用户发起回顾，就是授权整理本范围内已有的明确结论；不因此要求每条内容再走一次确认。新提出的重要产品决定仍需用户确认，不能借回顾替用户拍板。

### 保存必须满足的规则

- 回顾中的必要关联更新一起成立，不能出现记录已保存而其引用对象不存在的状态。
- 每项更正具有对应的修改前后和具体来源，不能出现内容已被覆盖、修订或出处却未保存的半完成状态。
- 只有成功保存后才推进对应来源的回顾边界。保存失败，不得宣称内容已经记录。
- 同一已保存范围再次回顾，识别已有结果并按需修订，不机械复制出另一组相同记录。
- 历史记录和修订保留当时含义；当前综述、设计保持当前认识。二者通过引用关联，不靠覆盖历史保持一致。
- 来源不足时明确留下缺口。不能用压缩后的会话摘要冒充已核对的完整原始对话。

这些是业务目标，不在此指定事务、锁或接口的具体实现。

## 7. 最小可用闭环

开发者建立一个项目并关联仓库，形成可阅读的项目综述和基本业务设计；随后使用 Coding Agent 推进一段需求，明确发起回顾。CoSeed 保存本次需求结论及来源，更新受影响的当前内容。开发者几天后回来，能够先读懂项目现在是什么，再查看需求时间线理解为什么变成这样，并继续工作。

第一版验收至少覆盖：

- 新读者从综述中理解产品、概念和实际用法；从业务设计进入相关模块理解实现策略。
- 一次回顾可以归并两个独立需求，分别产生记录，并且不把它们混成一个大需求。
- 再次回顾同一范围不产生一批重复记录。
- 更正任意一类内容后，都能查看每一次修改前后、操作者、修改时间和具体原始依据；来源缺失的 Agent 更正不覆盖当前内容。
- 修正一条旧记录后，可以看到修改历史；后来推翻旧决定时，能同时看到旧决定和新变化。
- 需求改变影响综述或设计时，相关当前内容同步更新，且能够追到对应记录。
- 切换项目、来源不可得、内容被别人先修改、保存失败时，不能出现跨项目写入、伪造来源或静默丢失内容。

当前内容与需求推进应能双向追溯：阅读一段综述或设计时，可以找到相关需求和变化记录；从一条推进记录也能回到受影响的当前内容。时间线服务于理解需求怎样形成，不成为与项目综述割裂的另一份日志。具体入口交互随后设计。

具体样例见[真实讨论的回顾示例](retrospective-example.md)。

## 8. 进入数据和接口设计前需确认

1. **来源输入怎样规范化**：回顾材料由 MCP 调用方提供，需确定原始片段、通用来源定位和客户端可选元数据的输入规范。不能假定 MCP 自动携带完整对话，也不把某个平台的消息标识作为唯一必需格式。
2. **状态更新入口**：六种状态及自由流转方向已确定；调用方如何提交变化依据、系统如何关联对应版本及拒绝冲突，仍需结合写入流程设计。
3. **同仓库的不同目录、分支及 worktree 怎样识别项目**：不能默认路径不同就是不同项目，也不能默认同一远程地址的资料都应合并。
4. **回顾失败或遇到人工修改冲突时怎样继续**：业务上保留已有内容、不静默覆盖；具体交互和批次恢复方式待设计。

以上问题不影响先 review 核心概念和业务边界，但在实现相应行为之前需要明确。
