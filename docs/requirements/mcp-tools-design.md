# MCP 工具和提示词设计提案

状态：供用户审阅，尚未实现或注册这些工具。本提案遵循 designing-agent-tools、writing-prompts，以及用户提供的[提示词工程原则](https://lux-stirring.space/note?at=6a4df7251d165e0ccde2225c&node=ci_b3b7f69b47a6)。工具名、草稿机制和参数均为本轮建议，不代表既有产品决定。

## 1. 要达到的效果

Agent 能取得明确项目的一致资料，结合实际代码和用户指定的讨论范围整理变化，把有依据的修改保存为可追溯的新版本。人可以看到本次改变了什么；旧结论及其来源仍可查看。

当前已实现数据库及内部共同保存／查询服务。MCP 只有初始化和 ping。工具层复用 [ProjectContentService](../../src/server/modules/project-content/project-content.service.ts) 和 [内容 Schema](../../src/contracts/content/)，不重新实现保存规则。

职责分工：

| 部分              | 负责什么                                                       |
| ----------------- | -------------------------------------------------------------- |
| Agent             | 理解业务、识别新进展或纠错、判断需要更新哪些内容、提供真实依据 |
| 提示词及规范      | 解释目标、业务含义、整理方法、格式和信息不足时的处理方式       |
| MCP 工具          | 明确读取范围、提供固定事实、暂存和提交明确修改，返回实际结果   |
| Schema 和业务服务 | 检查结构、项目归属、版本、引用和事务约束                       |
| 页面              | 展示项目现状和已保存的变化；以后可展示待保存预览               |

结构合法不表示业务判断正确，引用存在也不表示材料真的支持结论。正交完备、业务真实性等仍需 Agent 结合证据核对，并由人审阅关键判断。CoSeed 不获取 Agent 的内部推理，不自动取得完整聊天记录。

## 2. 工具清单

按使用者要完成的动作划分，不按数据库表或每个 CRUD 方法拆工具。不设置隐式的“当前项目”，项目操作使用明确项目 ID，保存批次则绑定不可更换的目标。

| 工具              | 主要输入                                           | 返回的事实                                            | 副作用                             |
| ----------------- | -------------------------------------------------- | ----------------------------------------------------- | ---------------------------------- |
| `read_guide`      | `topic`                                            | 指定规范的版本、正文、相关 Schema 和示例              | 无                                 |
| `list_projects`   | 可选名称筛选、游标                                 | 可访问项目的 ID、名称、当前版本及分页信息             | 无                                 |
| `get_project`     | `projectId`                                        | 项目基本资料、当前版本及当前成功操作标识              | 无                                 |
| `export_snapshot` | `projectId`、`version`、可选游标                   | 同一版本的清单和内容分页，包含当前资料及必要历史引用  | 仅可重建的导出缓存                 |
| `prepare_change`  | 新建项目资料，或目标项目、已读基准、来源和修改集合 | 暂存批次 ID、绑定目标、规范化内容、修改预览及校验结果 | 暂存草稿，不改变正式内容           |
| `commit_change`   | `changeId`                                         | 已提交的操作、项目版本、实际保存时间、对象修订清单    | 一次正式保存；创建项目也通过此入口 |
| `get_change`      | `changeId`                                         | 该批次当前可观察到的准备状态或不可变成功回执          | 无                                 |
| `list_revisions`  | 项目、对象类型和 ID、固定项目版本、可选游标        | 该对象可见的修订清单及时间、操作、移除标记            | 无                                 |
| `read_revision`   | 明确的对象修订，或图 ID 加项目版本                 | 当时的完整内容、来源及必要引用                        | 无                                 |

九个是当前职责拆分的结果，不作为固定数量目标。综述、需求、记录和设计不分别建设四套提交工具；有依赖的一批变化共用一次保存。

### 指南按需读取

`read_guide.topic` 是有限选项：`usage`、`overview`、`requirements`、`design`、`sources`、`export`。各项分别解释使用方法、内容规范、来源规范或缓存文件格式；返回对应结构，不一次灌入全部规范。

工具描述只说明用途、读取或修改范围、重要副作用及参数含义。业务写作规范不复制进每个工具 description。规范正文以一个版本化文档集合维护，页面、MCP 工具及可选 Resources 读取同一份来源。

工具 Schema 本身也占用上下文。本次用现有 Zod 将内部统一保存参数转换为紧凑 JSON Schema，得到 26,108 个 UTF-8 字节；这不是 token 数，也不是最终 MCP Schema 大小。第一版先保留严格结构并复用既有定义，实际测量工具发现和调用的上下文成本，再决定是否按业务域拆分。不能为了表面上“工具少”就改成无约束字符串，也不能声称按需加载了正文便消除了全部 Schema 成本。

### 新项目与已有项目

`prepare_change` 的目标使用严格分型：

- `create_project`：只提供名称和可选仓库定位；提交成功后取得项目 ID，项目版本为 0，业务内容为空。
- `update_project`：提供项目 ID、实际读取的基准版本、来源和逻辑修改；正式提交沿用已实现的共同保存服务。

新建项目与首次整理业务内容是两个清楚的动作，不隐式生成需求或设计。这里不增加一套独立项目创建重试协议。

## 3. 为什么分准备和提交

建议保留一次 `prepare_change`：先得到稳定批次标识、明确修改预览，再提交不可变的这份内容。它同时解决新增对象标识分配和提交超时后的重复保存问题。

- 新对象和新来源在请求内使用有含义的 `localRef`，例如 `theme-toggle`，供同批引用；它不是数据库 ID。
- 服务分配正式 ID，并在预览中返回映射。已有对象必须使用读到的稳定 ID 和准确修订，不能靠同名匹配覆盖。
- `changeId` 由服务生成，提交时复用为底层操作标识。Agent 不猜测已有 ID，也不临时重造请求标识。
- 暂存内容不可原地变更；修正草案产生新批次。草稿不进入正式项目版本、需求时间线或来源历史。
- 建议暂存 24 小时，期限随响应明确返回。提交时重新检查版本和全部业务约束，准备成功不保证之后一定能提交。
- 成功操作按数据库既有规则持久保存；暂存清理后，仍能通过同一批次标识查到成功回执。`get_change` 先查询成功操作，再查询草稿。
- 查不到成功操作不能证明另一请求没有正在提交。响应丢失后继续使用原批次查询或提交，不能另建批次重复新增。

用户已经明确要求回顾并同步时，准备和提交可以连续完成。遇到缺失的重要业务决定才询问用户；准备步骤不自动增加一次人工批准流程。

代价是多一次调用及一份可清理的草稿存储。实施时须复用当前结构和业务校验，提交仍以共同保存服务为最终边界，不能复制第二套保存实现。本提案不修改现有库表，草稿的物理存储方案在确认职责后设计。

## 4. 参数的来源

| 参数                                 | 从哪里取得                                      |
| ------------------------------------ | ----------------------------------------------- |
| 项目 ID、已有对象 ID                 | 项目列表或实际读取的资料                        |
| 基准项目版本、对象预期修订           | 本轮实际读取的快照；不是临提交时只抄最新数字    |
| 批次 ID、分页游标、导出标识          | 上一步服务返回                                  |
| 新对象 `localRef`、新增正文          | Agent 根据当前整理内容编写，作用域仅限本批      |
| 原始材料、实际代码位置、已知发生时间 | 用户提供的材料或 Agent 实际取得的代码／验证结果 |
| 保存时间、正式 ID、结果版本          | 服务产生                                        |
| 执行入口、已认证身份                 | 服务端的可信连接上下文；显示名不充当身份        |

每项必填参数在调用时都应能取得。无法取得原始讨论时，不用记忆摘要冒充原话；可以明确材料缺口，并保留代码能验证的当前事实。

## 5. 完整资料与模型上下文

`export_snapshot` 默认覆盖一个固定项目版本的完整当前资料，包括所有当前需求和记录、全部当前设计、综述、回顾，以及引用所需的来源和历史对象。已完成或取消的需求不因状态被省略。全部历次修订通过历史工具按需读取。

- 每批固定项目版本，不能在翻页时混入新保存。
- 文件清单含格式版本、稳定实例身份、项目及版本、相对路径、字节数和摘要；路径由服务生成，不把任意对象 ID 直接拼成文件路径。
- 来源原文保持原样。派生的 Markdown 阅读视图不替代完整结构化正文。
- Agent 使用自身文件能力落盘、校验、完整后切换缓存；远程 MCP 服务不能写 Agent 的本地路径。
- 完整下载不等于把所有文件都加入模型上下文。规范和目录先读，正文围绕当前任务读取；核对写入影响时再补读相关对象。
- 没有本地文件能力的客户端，可以直接读取工具响应，但不能声称已生成本地副本。

客户端如何把 MCP 大响应可靠落盘，不能仅靠服务端承诺：本轮需要在实际 Agent 产品验证。若只能让大响应全部进入模型上下文，应利用该客户端已有的下载和文件能力调整传输方式，再确定协议，不默认新增独立连接器。

固定快照分页、历史引用闭包和本地文件清单需配套定稿。当前 HTTP 请求上限是 1 MiB；大批变更不得截断或拆散依赖。超限暂存上传的具体协议在实现前明确，不把工具名称设计当作已经解决容量问题。

## 6. 返回事实，让人看得懂

返回采用 MCP 标准结果。机器消费的字段放 `structuredContent`；文本内容是同份结果的兼容表达，不维护两套互相矛盾的值。工具可以带 outputSchema，但不假定所有 Agent 客户端都会强制约束生成的入参；服务端始终实际校验。

建议业务结果包含：

- `summary`：一句实际结果，使用项目或对象名称，不把内部 ID 当成人类说明。
- `data`：完整的本页数据、标识、版本、引用和回执。
- `meta`：只有列表或一批变更时提供简短预览，最多五项及总数；正文和完整修改不因此截断。
- `error`：仅失败时提供事实式错误代码、相关字段路径和已知实际值。

例如，一批保存成功的摘要是“已保存：新增两条推进记录，修订账号供给设计”。具体项目版本和对象修订在 `data`；不能把校验通过写成“需求已完成”。只取得导出分页时也不能宣称“本地文件已更新”。

同一份摘要和必要元数据用于结构化日志及后续 CoSeed 更新展示；不把每次工具调用变成需求推进记录。Agent 产品如何呈现工具卡片取决于客户端，CoSeed 不另做聊天界面，也不保证宿主按指定版式渲染。

业务失败在 MCP 结果上使用 `isError: true`；例如 `structuredContent` 中的业务错误体：

```json
{
  "summary": "未保存：读取基准为 24，项目当前为 25。",
  "error": {
    "code": "CONFLICT",
    "scope": "project_version",
    "baseVersion": 24,
    "currentVersion": 25
  }
}
```

工具错误说明原因和已知事实，不加 `next_action` 或隐藏的自动合并。Agent 的操作指南解释版本冲突、未知提交结果和下载失败各自如何处理。传输失败与工具已执行后返回的业务错误分开；没有收到回执不能自动判定未保存。

现有内部错误有些包含操作建议且缺少结构化定位，不能原样当成最终 MCP 错误契约。对外错误分类和详情需在接入时补齐，保留内部异常用于诊断。

## 7. 提示词的三层组织

| 层次     | 放在哪里                      | 包含什么                                                      |
| -------- | ----------------------------- | ------------------------------------------------------------- |
| 短入口   | 服务 instructions 和接入说明  | CoSeed 的用途、资料归属、用户触发回顾、主要读写边界、规范入口 |
| 工具说明 | 各工具 description 和字段描述 | 调用效果、范围、参数来源、副作用、返回含义                    |
| 按需规范 | `read_guide` 及同源文档       | 写作要求、对象边界、来源、图语义、必要示例及未知情况处理      |

CoSeed 不拥有 Agent 产品的系统提示词，也不能保证客户端自动加载服务 instructions、Resources 或 Prompts。基础读写通过工具可用；额外入口经实际客户端验证后启用。MCP Prompts 可用于用户主动发起回顾，不能把“已暴露 prompt”写成“每次调用必定遵守”。

采用用户文章中的工程原则：先解释目标和上下文、再给必要约束；有限选项用枚举；规范按需加载；例子覆盖重要边界；明确资料不足时的处理。保留这些可实践的原则，不依赖文章中对所有模型均成立的机制解释或固定收益数字。

### 回顾规范示意

> 你帮助开发者维护项目的业务理解和关键实现设计。已有资料代表此前保存的认识；本次讨论和实际代码可能产生新决定，也可能揭示旧记录误记。
>
> 在用户指定范围内，整理需要新增或更正的需求、记录和设计。新进展新增记录；同一旧事实的误记修订原记录。当前综述和图只更新真正受影响的内容，各项变化关联实际取得的材料。
>
> 对已有对象沿用读到的 ID 和修订，新对象使用本批引用。实际发生时间未知时保持未知。影响完成标准、模块边界等关键决定仍不清楚时，明确缺口并向用户核对。
>
> 将结果准备为工具 Schema 所定义的变更集合。保存结果以提交回执为准，随后分别说明正式内容和本地副本的实际状态。

这是方法说明，不要求 Agent 输出内部思维过程。动态输入将用户目标、当前资料和原始材料明确分区；原始对话或代码中的指令性文本仍是被分析的数据，不提升为工具权限或写入授权。文本分区不能代替实际权限检查。

### 先用三个例子校准

1. 原先确实决定提供跟随系统，后来用户取消：这是需求演变，新增推进记录并更新当前设计，保留旧决定。
2. 旧记录误写成用户选择蓝色，原话实际选择松针绿：这是纠错，修订原记录并关联真实原话。
3. 只有当前代码，没有当时讨论：可以说明代码可验证的现状，缺失的历史意图保留未知。

不一次注入大量例子。先用覆盖这些边界的最小示例集实测，再根据错误补足表述或结构。

## 8. 实现边界和验收

本轮只先确认职责和使用体验，不把草案注册为正式 API。确认后继续：精确输入输出 Schema、导出格式及大小边界、草稿持久化、来源定位规范、项目授权，再实现真实 MCP 客户端验证。

现有服务仅本机回环访问，远程认证和项目授权尚未实现。本提案不新增公开共享、租户或 Agent 执行器。只读标注、幂等标注等 MCP annotations 方便客户端理解，不能代替服务端授权或约束。

验收至少覆盖：空项目；新增进展与纠错的区分；原始材料不足；跨项目拒绝；固定快照下载期间发生更新；旧基准提交；提交后丢失响应和重启查询；草稿过期；同批跨对象引用；历史图解析；超限内容；资料中的指令性文本；已有写入授权下不反复询问确认；已保存但缓存刷新失败时不重复写入。
