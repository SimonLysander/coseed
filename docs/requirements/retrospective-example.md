# 用 CoSeed 自身的讨论检验回顾模型

这是根据前期真实讨论整理的业务示例，不是已经导入服务的生产记录。使用下列用户原话和已验证原型说明结构；未核实的发生日期不编造，保存时间也不代替发生时间。

## 项目

**CoSeed**：帮助人与 Coding Agent 共同理解项目需求、设计及其演变。本例所有需求和记录都归属于该项目。

## 需求一：让读者理解项目的核心概念

读者需要先理解业务中的名词和关系，再阅读使用示例、参与设计判断。完成标准是：词条解释清楚、关系有明确语义、层级不混淆，并可从图定位到解释。

### 记录：明确核心概念的内容边界

核心概念要覆盖整个被说明项目，解释理解业务必需的名词、关系和容易混淆的区别。原来只写账号、企业持有和员工使用，范围偏窄；定义应先说明是什么，再补充关键区别。“申请”也包括完成、驳回和撤回后的记录，不能只定义成等待处理的请求。

来源：用户提出“review 一下核心概念这块，到底应该放哪些内容、怎么展示？规范是什么”，随后认可内容梳理方向。

### 记录：确定关系和词条的展示方式

采用上方概念关系图、下方双列释义列表，共用一份概念与关系数据。关系区分种属、组成和具体业务关联；列表缩进只表示种属，每个概念只解释一次。词条全部展开，点击图中概念定位到对应释义。

来源：用户澄清需要“通用的关系”，并认可“关系图＋有层级的双列释义列表”方案，要求实现到页面。

### 记录：完成阅读原型并核对交互

原型已呈现 15 个概念及其关系，用户角色和费用类别按种属缩进。图节点与词条使用相同标识，点击节点可定位并突出对应释义。已通过结构、引用、循环、布局、转义检查及真实浏览器定位验证；这只证明阅读原型完成，不代表正式服务或需求管理已经实现。

来源：原型实现和验证结果；正式纳入系统时应关联对应代码与验证材料，不能只保存这段总结。

## 需求二：让长篇项目综述能够快速定位阅读位置

读者在阅读项目综述时，需要快速找到章节，知道当前读到哪里，并在同页定位时保留图形和页面内容。这个目标可以独立于概念模型和图的内容进行验收，因此另立需求。

### 记录：确定右侧阅读目录

页面左侧继续承担项目内容导航，页内目录放在右侧独立阅读栏。目录包含产品是什么、核心概念、使用示例以及示例小节；点击目录定位正文，滚动正文更新高亮。用户明确选择右栏方案，因此没有把此前讨论过的左栏目录提议写成已经实施的事实。

来源：用户原话“放在右边栏目吧；专门阅读”。

### 记录：完成章节定位原型

阅读原型已提供右侧目录、同页章节链接、滚动高亮及刷新后的章节定位；选择章节不重新创建当前页面中的图。窄屏时目录折叠到正文上方。已验证页面切换、浏览器返回和窄屏定位，正式服务中的项目切换仍需后续实现。

来源：阅读目录原型和浏览器验证结果。

## 当前内容怎样变化

对需求一，当前综述应描述已经确定的概念解释方式，设计中保留关系图和词条如何共用内容。需求二改变的是阅读导航设计，不应重新定义“核心概念”本身。

一次回顾可以同时保存两项需求的记录，并更新对应当前内容。回顾作为一次整理工作保留来源范围和处理结果，不因此再建立一个“这一下午开发”的大需求。

## 哪些情况修改，哪些情况追加

**修正旧记录**：如果记录误写成“所有缩进都表示组成”，而当时实际确定的是“缩进只表示种属”，应修订原记录，保留修改前后、执行者、修改时间，以及支撑“缩进只表示种属”的具体对话材料。不能只在更正历史里写“Codex 修改”。它是纠错，不冒充后来新发生的产品决定。

**追加新记录**：如果后来用户真的决定缩进改为表示组成，应新增变化记录，引用旧决定并说明新规则，同时更新当前设计。不能直接改掉旧决定，让历史看起来从未发生过变化。

**统一影响多个地方**：用户后来要求“这个页面的所有的图都固定适应画布，不可以放大缩小”，这一约束影响概念图和使用示例图。一次回顾应关联受影响内容并核对实现；图的类型不同不意味着必须复制成几份同义的需求。

## 这个例子检验什么

- 需求按独立用户目标划分，不按聊天、时间段或技术文件划分。
- 记录按结论与结果划分，不按工具调用划分。
- 早期提议、最终决定和实现结果不是一回事。
- 当前内容、推进记录、修订历史分别承担职责，通过来源和引用连起来。
- 每一次更正都有具体出处，来源信息与修改内容一起保存；更正历史不因它未产生新业务进展而省略。
- 来源或发生时间尚未具备时明确缺口，不用看似完整的记录掩盖未知。
