# 历史记录的共同要求

适用范围：项目资料、综述、需求、推进记录，以及后续可维护的设计内容。这里约定共同语义，不增加一张万能历史表，也不表示尚未实现的存储服务已经具备这些保证。

当前采用数据库权威存储；项目快照、本地读取副本及 MCP 保存流程见[存储及 Agent 读写流程](storage-and-agent-flow.md)。对象修订号标识单个对象的历史；项目内容版本标识整份一致快照，通过同一次保存操作对应，不使用 Git commit 管理资料版本。

## 1. 每份历史至少能回答什么

| 问题               | 必须保存或可可靠取得的信息                             | 谁负责                                               |
| ------------------ | ------------------------------------------------------ | ---------------------------------------------------- |
| 改的是谁           | 项目 ID、业务对象 ID及对象种类                         | 调用方指明目标，系统校验归属                         |
| 是哪一版           | 对象内唯一且有顺序的版本号、当前版本指向               | 系统分配和维护                                       |
| 当时是什么         | 本版完整内容，包括状态、重要归属和关系；前版内容也保留 | 系统保存快照                                         |
| 何时保存           | 每版关联的写操作 saved_at，首版也必须有                | 服务端自动记录                                       |
| 谁通过哪里提交     | 操作者信息、Web/MCP 等入口、实际可获得的调用上下文     | 系统记录已有身份及入口；未认证的自述不能冒充认证身份 |
| 根据什么改         | 不可变的来源片段、定位、针对本版具体修改的引用         | 调用方提供材料，系统校验和保存引用                   |
| 为什么改           | 修改说明，或关联结论与来源的解释；未知不伪造理由       | 内容提供者说明，系统保留                             |
| 哪些属于同一次保存 | 写操作 ID及实际产生的版本，可关联回顾                  | 系统原子保存，支持提交重试识别                       |

“修改了什么”可以通过本版与前版快照比较取得，不要求重复存一份差异。不能只保留一个随当前内容覆盖的 updated_at，也不能仅保存一句“Agent 更新了项目”。

执行者、提交入口、原决定提出者是不同信息。例如 Agent 整理用户的决定，保存执行者可以是 Agent，原始表达者应从来源识别，不能把两者混成一个人。

## 2. 时间分开表达

- **首次收录时间**：对象首次进入系统的时间，与首版保存时间保持一致。
- **每版保存时间**：本版何时落库，从本版关联的写操作读取；正文修订和状态变化都因此可追溯。
- **业务实际发生时间**：例如某条结论实际形成的时间，有可靠材料才填写；未知为 NULL，不用保存时间填补。
- **当前状态的最近变化时间**：从最近一次状态真的改变的版本取得，不等于需求的最近修改时间。

不同对象的版本可以在同一写操作中保存，因此时间可能相同。时间不是唯一键，不用毫秒差判断版本先后；也不能用随机对象 ID 推断业务时间顺序。

业务事件时间按对象实际含义设计，不强迫所有历史内容都有同一种 occurredAt。例如推进记录已设计 occurredAt；状态如果要补录独立的业务生效时间，须另外明确字段及依据，当前先保留系统实际记录状态变化的时间。来源自己的发生时间也不能未经判断就等同于状态生效时间。

## 3. 状态历史如何得到

状态是需求版本的字段；本轮不另建一张重复维护的状态历史表。按版本顺序读取需求快照：首版建立初始状态，此后只有状态值不同才产生一项状态变化展示。

例如：

| 需求版本 | 保存时间（示意） | 状态     | 展示为状态变化 |
| -------- | ---------------- | -------- | -------------- |
| v1       | 14:00            | 设计中   | 是：初始状态   |
| v2       | 14:30            | 设计中   | 否：仅补充描述 |
| v3       | 15:30            | 方案已定 | 是             |
| v4       | 16:00            | 方案已定 | 否：仅修正措辞 |

当前状态变化时间仍为 v3 的 15:30，需求最近修改时间则为 v4 的 16:00。每个版本本身的保存时间都保留，状态未变不会伪造新状态事件。

状态变化在页面上可以组合显示为“原状态、新状态、记录时间、修改者、依据、对应需求版本”；这些信息由状态快照与保存元数据组成，不要求 Agent 在状态字段里提交一个时间对象。

真实业务状态变化关联支撑它的推进记录及具体版本，一次变化可以由多条记录共同支撑；相关保存一起成立。首次建立需求和纠正误记可直接使用原始或更正来源，不强迫制造推进记录。旧记录后续被修订时，原状态变化继续引用当时的版本。

没有不可逆终态，允许回退、恢复和跳转。回到过去曾有的状态仍是一次新变化，不能和早先那次状态记录合并。完成、取消后重新推进也不能擦除曾经完成或取消的历史。

## 4. 历史关联与保存边界

- 历史引用固定到具体对象版本；打开当前对象则走稳定对象 ID与当前指针，二者用途分开。
- 所属需求、来源引用或关联对象被纠正时，旧版本的关系仍应可读，不能只保存当前关系覆盖历史。
- 修正旧结论的记载，生成原对象新版本；后来产生新决定，则按业务边界新增推进记录。修订历史不自动冒充业务推进。
- 来源说明补充或纠错也保留新旧引用，不直接修改旧材料或事后给旧版悄悄添证据。
- 一次保存的当前版本、历史和来源引用一起提交；失败回滚，旧内容保持有效。第一版以项目内容版本校验读取基准，并在同一事务中检查依赖、推进版本和保留成功操作结果，避免静默覆盖及超时重试产生重复修订。

## 5. 检查能力的边界

类型、外键和服务规则可以检查字段、项目归属、引用、版本冲突和原子性。它们不能自动证明来源真实、材料足以支持结论、需求确实完成。

这份规范是各模块后续落库与验收的共同依据；现阶段已有的内容 Schema 不接受系统保存时间、操作身份或历史快照混入正文。完整物理表和业务保存服务尚未接入，不能把提案或示例通过校验当成所有历史能力已经完成。
