# 项目综述的内容结构

状态：**结构已进入运行 Schema、数据库、HTTP/MCP 及综述阅读页。** 本文解释“内容由什么组成、如何互相引用”；实际读写和页面边界见 [项目入口与综述](../requirements/project-workbench.md)。

基于已经确认的三部分和原型规则，提供[完整 JSON 示例](overview-content.example.json)及[可执行结构草案](overview-content-draft.ts)。示例描述 CoSeed 的预期业务用法，不是已经导入的内容，也不表示这些业务已经实现。

## 1. 一份综述的结构

```text
schemaVersion：内容结构版本，当前为 1
content
├── product
│   └── markdown：产品整体表述
├── concepts
│   ├── entries[]：概念 ID、名称、解释
│   └── relations[]：关系 ID、种类、两端概念，业务关联另有标签
└── examples
    ├── introductionMd：整组示例的背景和前提说明
    ├── actors[]：业务角色 ID、名称
    ├── useCases[]：用例 ID、名称、参与角色 ID
    └── sections[]
        ├── id：小节的固定身份
        ├── title：可修改的小标题
        ├── diagram：图 ID、本节涉及的用例 ID
        └── markdown：本节例子正文
```

产品 Markdown 保留原始段落格式。核心概念的关系图和释义列表共用 entries 与 relations。示例角色和用例各定义一次；每节的图通过用例 ID 选取内容，再从用例取得参与角色，不在每张图里重复定义同一个角色和用例。

页面先展示整组示例的背景说明，交代谁在使用、当前情况与前提，以及这组例子要说明什么；再按“小标题 → 本节用例图 → 正文”逐节展示。背景说明采用自由 Markdown，每节独有的前提写入该节正文。小节与图直接归在同一对象中，改标题不会断开关联；不再用标题文本匹配图，也不靠正文包含某个字串来判断图是否正确解释正文。

## 2. 字段约定

| 对象         | 字段                            | 含义                                            |
| ------------ | ------------------------------- | ----------------------------------------------- |
| product      | markdown                        | 自由 Markdown；产品表述是首份可读综述的必要内容 |
| examples     | introductionMd                  | 整组示例的开篇背景说明，采用自由 Markdown       |
| 概念 entries | id / name / descriptionMd       | 稳定身份、名称、Markdown 解释                   |
| 概念关系     | id / kind / source / target     | 稳定身份、关系种类、两端概念 ID                 |
| 业务关联     | label                           | 从 source 到 target 读得通的业务关系名称        |
| actors       | id / name                       | 示例中的业务角色；不是本次保存的执行者          |
| useCases     | id / name / actorIds            | 用例身份、用户目标、参与角色                    |
| sections     | id / title / diagram / markdown | 小节身份、标题、对应图、自然段正文              |
| diagram      | id / useCaseIds                 | 本张图身份及涉及的用例                          |

ID 在各自集合内唯一，含义和展示位置改变时继续保留；名称、标题和数组下标都不当身份。跨版本匹配使用“对象种类及稳定 ID”，当前版本内的顺序由数组表达。修改文字不要求重建 ID。

`schemaVersion` 是内容结构的版本；数据库中的 `revision_no` 是内容修改次数。两者分开。保存到既有库表提案时，将 schemaVersion 写入 `schema_version`，content 写入 `content_json`，正文内部不再重复一份结构版本。

项目 ID、修改时间、执行者、来源及修订历史由外层记录维护，不放进正文重复保存。后续需求记录和设计对象通过稳定 ID 建立明确关联，本次不预埋没有目标类型和校验依据的任意 ID 数组。

## 3. 概念关系

| kind        | source → target 的含义    | 展示                                             |
| ----------- | ------------------------- | ------------------------------------------------ |
| kind-of     | 子类 → 父类               | 标签由类型生成“是一种”；只用这一关系推导词条缩进 |
| composition | 整体 → 部分               | 标签由类型生成“包含”，不产生种属缩进             |
| association | 按 label 表达具体业务关系 | 例如综述 → 来源：“以其为依据”                    |

种属和组成分别检查循环，关系端点必须存在。固定标签从类型生成，避免同一含义同时维护类型和固定文字。业务关联可以形成环，不能把业务关联图整体强制当成一棵树。

旧原型暂有限制“单一种属父概念、所有关系均禁止自关联”，这属于呈现约束，尚无事实表明应成为长期业务规则。本次草案只限制层级关系无环，未把单继承和禁止业务自关联固化。当前阅读页由 ELK 布局完整关系，释义列表每个词条只出现一次，按 entries 顺序展示；不将整个关系图强行改成单父树。

本结构只能判断关系完整、自洽，无法证明“某个概念确实属于另一个概念”；业务含义需核对来源。

## 4. 用例图的边界

本版沿用原型已经使用的“角色参与用例”关系。参与关系由 useCases.actorIds 表达，同一角色可参与多个用例，同一用例可被多个小节选用。系统边界和系统名称由项目上下文提供，角色在边界外，用例在边界内；连线不表示执行先后。

diagram 中不保存坐标、字体、配色、尺寸、SVG、Canvas 指令或图形引擎实例。布局由呈现层计算，更新布局算法不产生业务修订。

include、extend、用例泛化及跨系统边界尚未纳入这份提案，也不把“任意连线类型”作为扩展口。需要时明确含义和校验规则，再演进内容结构版本。

## 5. 校验边界

草案会拒绝：

- 空白的必填正文、名称、解释，以及未知结构字段或不支持的结构版本；
- 集合内重复 ID、重复关系、缺失的概念／角色／用例引用；
- 种属或组成循环；
- 已填写的示例小节缺图、缺正文，或图不包含任何用例；
- 角色引用重复、用例引用重复、没有任何用途的角色和用例、重复的图 ID。

草案允许明确留空的 concepts 与 examples 集合，避免尚未掌握材料时编造内容；尚无示例小节时，introductionMd 可明确为 null，也可先填写已有的背景说明。有示例小节时必须提供非空白的开篇背景说明。产品表述不能为空。结构合法不代表综述已经完整。是否具备所有必要概念和示例，属于后续内容质量与写入规范，不在此增加未确认的“草稿／发布”流程。

正文是否解释清楚、图是否准确对应本节语义、来源是否真正支撑结论，均不能由字段校验自动证明。校验不会偷偷 trim 或改写 Markdown。

## 6. 下一步如何使用

确认这份结构后，将可执行草案迁入 `src/contracts/overview/` 作为唯一类型及校验入口；前后端共同消费，示例仅用于测试和开发展示，不灌入个人项目数据。

然后再接入已确认方向的八张表、事务保存和读取，最后设计 Agent 的调用方式与写作规范。本次没有新增接口、修改数据库或替换当前阅读样板。

验证命令：`npm exec vitest run tests/contracts/overview-content-design.test.ts`；类型检查：`npm run typecheck`。这些检查验证提案本身，不是 MCP 或真实内容的业务验收。
