# 数据库存储实现

这是当前运行实现。MCP 已通过共同服务读写，固定版本文件读取已实现；项目入口及综述阅读已接入，其余业务页面尚未接入，不存在绕过校验的公开数据库写入接口。

## 权威定义

| 位置                                   | 负责什么                                   |
| -------------------------------------- | ------------------------------------------ |
| `migrations/0000_coordination.sql`     | 项目身份、成功操作及版本推进               |
| `migrations/0001_project_overview.sql` | 原始来源、项目资料及综述                   |
| `migrations/0002_business_design.sql`  | 节点、连线、技术说明、图及成员             |
| `migrations/0003_requirements.sql`     | 需求、推进记录、回顾、状态依据及跨模块关联 |
| `src/contracts/content/`               | 综述、需求推进和业务设计的运行内容 Schema  |
| `src/contracts/project-content.ts`     | 内部逻辑修改、来源引用、读取结果和保存回执 |
| `src/server/modules/project-content/`  | 计划修订、完整校验、事务保存和快照查询     |
| `src/server/database/schema/`          | 与真实 SQL 一致的 Drizzle 查询列映射       |

共有 38 张业务表，另外由 Drizzle 管理迁移记录表。业务表数是身份、修订、类型化引用和不可变来源的结果，不是扩展指标。SQL 保留原生延迟外键、生成列、STRICT 表和封存触发器，避免把这些约束替换成应用约定。

SQL 迁移是 DDL 权威。Drizzle 查询映射只描述列，不重复维护全部约束；不要用 `drizzle-kit push` 或普通自动生成把这些映射覆盖到数据库。新增迁移使用 `npm run db:migration -- --name=具体变更名`，审查自定义 SQL，并用真实迁移测试。已应用的迁移不可改写；后续变化新增迁移。

## 内部服务如何调用

`ProjectContentService` 是共同业务边界，MCP 已复用它，Web 后续沿用。业务模块本身不注册协议入口；MCP 适配见 [工具规范](../requirements/mcp-tools-design.md)。

- `createProject(input, context)`：保存实际创建请求及项目资料，结果为项目版本 0；不生成假综述或需求。
- `save(input, context)`：一批对象修改、来源和可选回顾归属共同提交，返回一份成功操作回执。
- `readSnapshot(projectId, version?)`：读取当前或指定的完整项目内容；图成员按同一版本解析。
- `readRevision(...)`、`readHistory(...)`：定位具体修订，或按修订号倒序分页浏览历史。
- `readSources(...)`、`getOperation(...)`：读取固定版本可见的原始来源和既有保存回执。
- `listProjects(options)`：名称子串筛选、按稳定 ID 分页；`readProject` 仅读项目资料及当前版本，避免元数据读取加载整张图。

这些是进程内调用，不是远程工具清单。`context` 由可信入口独立提供，保存实际入口、执行者类型、显示名和辅助定位。显示名不构成认证；远程授权仍待实现。服务保证数据项目归属，不能代替入口权限。

## 一批修改包含什么

请求包含 `projectId`、稳定 `operationId`、读到的 `baseVersion`、新增原始 `sources`、对象 `changes`，以及可选 `retrospectiveId` 和保存说明。系统保存时间、对象创建时间和结果版本由服务产生。

每项修改有 `objectType`、稳定 `id`、`expectedRevision`、`citations`。新对象的预期修订为 `null`，修改旧对象必须提供准确当前修订。一个对象在一批中只出现一次。项目资料和综述的 ID 均为项目 ID；节点种类不可原地更换。

- `upsert` 提供完整内容。需求和记录的 `links` 未提供时沿用，显式 `[]` 才清空；回顾的 `inputSourceIds` 同理，但有效回顾至少保留一份输入材料。
- `remove` 新增保留原内容的移除修订，需要修改前依据；项目整体移除不在此服务范围。
- `restore` 从同一对象的有效历史修订复制完整内容和关联，追加新修订；不回退项目指针。已移除对象必须显式恢复，不能用普通保存悄悄复活。

没有内容、关联、移除状态或来源引用变化的请求返回 `NO_CHANGES`，不制造版本。集合成员排序后比较；正文和原始来源不修改空白或换行。

来源不可覆盖。旧 ID 仅可重复提交完全一致的材料；更正材料使用新 ID。请求以 RFC 8785 JSON 规范化及 SHA-256 指纹识别重试，来源顺序、图成员集合顺序不影响指纹，修改项顺序保留推进记录的首次捕获顺序。同操作同请求返回原回执，同操作不同请求拒绝。

## 来源引用的边界

每条依据有 `sourceId`、修改前／后的 `side`、JSON Pointer `path` 和凝练的 `explanationMd`。空路径表示整个对象。保存至少有一条修改后引用；移除至少有一条修改前引用。变化字段都需要覆盖，清除字段需要覆盖旧位置。内容文档还包括需求／记录 `links` 和回顾 `inputSourceIds`。

系统检查路径真实存在、引用不重复、原始来源同项目且已捕获，以及变化位置被覆盖。路径仅匹配自身 JSON 字段，不接受原型链、数组 length 或非法转义。它不能自动证明一段对话真的支持业务结论，原始材料及说明仍须由调用者如实提供。

节点的 `primarySourceId` 若非空，须引用代码材料及规范的仓库相对 `locator.path`；`typeSourceId` 须引用已捕获并被本修订引用的材料。TS 类型只保存展示文本，不执行。目录归属的真实性需要 Agent 结合实际仓库核对，服务不声称已扫描业务代码。

## 需求、时间和关联

新需求保存初始状态依据；已有需求真正改变状态时，必须提供 `progress` 或 `correction`、原因及相应依据。`progress` 至少固定一条属于该需求的具体记录修订；同批新增记录也可以成为依据。状态未变不能伪造迁移。历史依据不会随记录后续更正或重新归类而漂移。

`occurredAt` 是已知实际发生时间，未知保留 `null`。`savedAt` 是系统保存时间，`createdAt` 是对象首版保存时间。记录另保留首次操作的项目版本和请求内顺序，修正记录不重排首次捕获次序；这不替代尚未确定的页面默认时间线排序。

需求关联当前综述部分或当前设计对象；删除被引用部分必须同时更新这些关联。记录关联固定对象修订；关联图时固定 `diagramId + projectVersion`，不能只用图自身修订号代表完整图。相同快照下所有成员、归属和技术说明一起解析。历史引用可以指向今天已移除对象的旧有效修订。

## 事务及读取

写事务先核对已成功操作及项目基准，再插入来源、身份、完整修订和关联，验证整个候选快照及当前指针，最后插入成功操作封存，推进项目版本后提交。所有失败整批回滚。事务内不调用网络、模型或生成文件。

读取快照在短一致读事务内完成。按对象批量选修订和成员，避免每个节点另查一次。返回来源覆盖当前内容直接引用及回顾输入；历史关联目标的全部内容和来源需通过历史读取补齐，不把当前快照误称为包含全部历史的离线文件包。缓存导出和分页传输属于下一阶段。

`tests/storage/` 使用正式构建服务、真实临时 SQLite 库验证迁移、回滚、项目隔离、重试、状态依据、历史关联、共享图、移除恢复及重开；`verify:database` 保留低层 SQL 回归。容量、吞吐及跨平台结论仍需部署阶段实测。
