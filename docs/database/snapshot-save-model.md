# 项目快照、保存操作及对象修订

状态：**供审阅的数据库模型提案，尚未执行迁移或接入业务服务。** 承接[已确认的存储流程](storage-and-agent-flow.md)。本文收口共同版本模型；业务字段继续由综述、需求推进和业务设计模块定义，不新建一张万能对象表。

## 1. 先看一轮真实保存的形状

以下 ID、版本和时间均为演示数据。

```text
projects：项目 P，当前内容版本 24
    │
    ├── 需求 R：当前修订 3
    ├── 记录 N：当前修订 1
    └── 节点 E：当前修订 2

一次保存 op-A（基准 24，结果 25）
    ├── 需求 R / 修订 4：新描述或新状态
    ├── 记录 N / 修订 2：纠正原记录
    ├── 记录 M / 修订 1：后来形成的新结论
    ├── 节点 E / 修订 3：更新职责
    └── 原始来源及各修订的具体引用
          ↓ 全部写完并校验后
project_versions：登记 P / 25 → op-A，封存本次内容
projects：当前内容版本 24 → 25
          ↓ 同一个数据库事务提交
页面可读 25，Agent 可导出 25；24 的内容仍可重建
```

三者关系是：**项目版本登记一次完整保存；保存操作说明谁、何时、基于什么提交；对象修订保存本次实际变化的内容。** 一次保存不是一条推进记录，一次回顾也不强制只对应一次保存。

## 2. 项目快照怎样存

不为每个项目版本复制整份内容，也不增加一张保存全项目 JSON 的快照表。增加一张很小的 `project_versions` 登记表，实际正文仍在各模块的修订表。

### projects：稳定项目身份和当前指针

| 字段                    | 含义                                                                             |
| ----------------------- | -------------------------------------------------------------------------------- |
| id                      | 稳定项目 ID，隔离所有资料                                                        |
| current_content_version | 整个项目当前内容版本，从 0 开始                                                  |
| current_revision_no     | 项目名称、仓库定位等“项目资料”自身的当前修订；沿用既有模型，不能当成整个项目版本 |
| created_at              | 服务端首次建立项目的 UTC 毫秒时间                                                |

当前正文不在身份表重复保存。各业务身份表同样只保存身份、归属、当前修订等必要信息。

### project_versions：项目版本登记

| 字段                         | 约束及含义                                     |
| ---------------------------- | ---------------------------------------------- |
| project_id + content_version | 联合主键；版本仅在本项目中有意义               |
| operation_id                 | 同项目保存操作；每次成功操作只登记一个项目版本 |

不重复存保存时间、执行者、正文、每个成员 ID 或“最新”标志，它们分别由操作、修订和当前指针给出。登记表和操作之间相互校验项目及结果版本，不能把版本 25 指向产生版本 26 的操作。

新项目在创建事务中登记版本 0，同时保存项目资料的修订 1、创建操作及人工输入来源。此时还没有综述、需求或设计对象；“空项目”不表示连项目名称和来源都没有。

以后每次实际改变正式内容的保存递增一次。读取、导出、缓存刷新、失败、相同操作的重试不增加版本；没有变化也不制造空操作。按版本顺序排列，不用时间戳或随机 ID 判断先后。

## 3. 保存操作怎样存

沿用 `write_operations`，增加项目基准及结果版本语义。这里只存已经共同成立的成功操作；校验失败不是一条成功历史，不提前设计后台任务状态机。

| 字段                    | 谁负责及含义                                                                     |
| ----------------------- | -------------------------------------------------------------------------------- |
| id                      | 操作稳定标识；同一次逻辑提交的重试保持不变                                       |
| project_id              | 目标项目；所有新修订和来源必须属于该项目                                         |
| base_content_version    | 调用方实际读取的基准；只有创建项目为 NULL                                        |
| result_content_version  | 普通保存为基准加一，创建为 0；由数据库生成，不让调用方另填一个可能冲突的结果版本 |
| request_hash            | 规范化逻辑请求的 SHA-256，用于判断同标识是否同载荷                               |
| entrypoint              | web / mcp / cli / system                                                         |
| actor_kind、actor_label | 实际可获得的执行者类型和显示信息；标签不冒充认证身份                             |
| client_metadata_json    | 已获得的客户端定位等辅助信息，不存凭据，不拿它代替原始来源                       |
| note_md                 | 可选的本次保存说明，不代替各对象的具体依据                                       |
| saved_at                | 服务端实际保存时间，所有本次新修订共享该时间                                     |

初始操作以外，一次保存只能以当前项目版本为基准；第一版不自动合并不同对象的并发修改。

请求哈希针对项目、基准、逻辑修改和来源等实际输入，排除服务生成的保存时间、分配结果和重试传输信息。建议采用 [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) 的 JSON 规范化后计算 SHA-256，具体请求字段随 MCP 契约固定；原文字符串不能 trim 或改换行。不能把普通对象键顺序差异误判成不同请求，也不能只比较原始 JSON 字节。

同标识同请求返回原成功结果；同标识不同请求明确拒绝。查询和重试必须先验证项目权限，再查既有操作；不能先因基准已落后拒绝一次其实已经成功的重试。哈希本身不作为跨操作的业务去重键，不同操作即使相似也可能是真实的新决定。

不再增加一张重复的操作结果表：回执由不可变的操作、项目版本及本次产生的修订生成，包含操作 ID、新项目版本、保存时间和修订清单。来源清单同样可从首次收录关系取得。大批上传的临时会话和失败日志不属于这张成功历史表。

## 4. 对象修订怎样存

沿用“稳定身份＋当前指针＋不可变修订”，各模块独立维护自己的表。

| 对象     | 身份表                 | 修订表                          |
| -------- | ---------------------- | ------------------------------- |
| 项目资料 | projects               | project_revisions               |
| 项目综述 | project_overviews      | overview_revisions              |
| 需求     | requirements           | requirement_revisions           |
| 推进记录 | progress_records       | progress_record_revisions       |
| 回顾结果 | retrospectives         | retrospective_revisions         |
| 设计节点 | business_entities      | business_entity_revisions       |
| 设计连线 | business_relationships | business_relationship_revisions |
| 设计图   | design_diagrams        | design_diagram_revisions        |
| 技术说明 | technical_notes        | technical_note_revisions        |

本表约定共同映射，不表示需求、回顾及其全部跨模块关联已经有正式 SQL。现有内容 Schema 继续约束正文；本轮不改变状态文案、节点种类或线类型。

各修订至少有：

| 信息                  | 存储位置及约束                                                            |
| --------------------- | ------------------------------------------------------------------------- |
| 项目、对象 ID、修订号 | 联合唯一身份；同对象从 1 递增，不随标题变化换身份                         |
| operation_id          | 同项目操作；同对象在一次保存中至多一版                                    |
| 完整内容              | 类型明确的 JSON 或该模块约定的列；保留本版全文，不只存 patch              |
| schema_version        | 内容结构的解析版本，不随正文每次修改递增                                  |
| 发生时间              | 仅有此业务语义时保存，例如记录 occurred_at，可为 NULL                     |
| 移除标记              | 可移除对象采用版本化 `is_deleted`，初始为 false；项目整体删除不在本轮范围 |

对象修订不再重复保存项目内容版本、执行者、保存时间；通过 operation_id 可靠取得。既有项目／综述草案的 previous_revision_no 可继续表达前版；其他模块不为历史读取额外复制前后链，排序以同对象修订号为准。

移除时新增一个保留原内容的修订并设置 is_deleted=true；不得物理删除身份或旧修订。恢复同一对象再新增修订、清除标记。读取快照时必须**先取当时最后一版，再过滤被移除的对象**，不能先过滤删除版而把更早的有效版本“复活”。需求取消仍是状态，不等于移除。此字段是存储提案，不表示新增任何删除界面或工具；旧模块 SQL 尚需合并此约定。

身份表的当前指针是由事务维护的查询投影，必须等于最新已提交修订。读取旧项目快照不能使用今天的 current_revision_no。

## 5. 如何重建项目版本 24

对每种对象：查出本项目中由版本不大于 24 的成功操作产生的修订，再为每个对象选最后一版。对象当时尚未创建，就不出现在快照中；后来才改名、换主需求或移除，不影响 24。

以需求为例：

```sql
WITH ranked AS (
  SELECT r.*, v.content_version,
         row_number() OVER (
           PARTITION BY r.project_id, r.requirement_id
           ORDER BY v.content_version DESC
         ) AS position
  FROM requirement_revisions r
  JOIN project_versions v
    ON v.project_id = r.project_id AND v.operation_id = r.operation_id
  WHERE r.project_id = :project_id AND v.content_version <= :version
)
SELECT * FROM ranked WHERE position = 1 AND is_deleted = 0;
```

版本查询先确认该项目确有目标 project_versions 行，不把不存在的 999 误读成最新状态。对象修订表保留 `(project_id, object_id, revision_no)` 主键、`(project_id, object_id, operation_id)` 唯一约束及 `(project_id, operation_id)` 查询索引；登记表保留版本和操作两个方向的唯一定位。字段及索引合并后用实际执行计划和数据量验证，不在设计阶段宣称达到某个吞吐。

同一导出绑定一个项目版本及导出格式，所有种类使用同一基准；图、成员和来源按引用闭包补齐。可先在短一致读事务中取齐不可变内容，再生成临时文件并分页传输，不为等客户端下一批调用长期持有数据库事务。[SQLite 事务语义](https://www.sqlite.org/lang_transaction.html)

不增加永久的 `snapshot_objects` 全量成员表。若以后实测重建慢，可建立可重建的导出缓存或检查点，不改变原始修订和版本登记的权威关系。

## 6. 来源和引用如何关联

### 原始来源

`sources` 保留既有字段：id、project_id、captured_by_operation_id、kind、raw_text、content_hash、locator_json、occurred_at。原文不可改；来源首次收录时间从操作取得，原始发生时间可未知。

每类修订使用自己的来源关联表，例如 `requirement_revision_sources`。关联精确指向项目、对象及修订，并保存 source_id、修改前／后、内容路径和支撑说明。一个来源可以被多次引用；但一次更正不能只笼统关联整次回顾。

### 业务及历史引用

| 关系                     | 具体定位                                                  |
| ------------------------ | --------------------------------------------------------- |
| 当前需求关联某模块       | 稳定模块 ID，查询时按选定项目快照解析                     |
| 图采用一个节点           | 节点 ID＋指定修订，沿用图的明确版本成员表                 |
| 新记录承接或推翻旧记录   | 旧记录 ID＋修订及关系说明                                 |
| 状态变化由记录支撑       | 需求修订 → 一条或多条记录的指定修订                       |
| 引用综述的某个概念或示例 | 综述修订＋内部对象种类及稳定 ID；内部对象合法性由服务检查 |

使用真实的类型关联及同项目复合外键，不增加任意 target_type＋target_id 的万能外键。引用目标必须已在该项目快照内存在，或者属于同一次提交；固定历史引用可以指向当时已有的旧修订，不能引用未来操作。移除后历史引用仍可打开，当前稳定引用则必须明确处理“已移除”，不能按名称换一个对象。

真实状态变化的原因、类型及记录版本关联放在需求修订的关联中；正文修订但状态未变不产生状态事件。首次建立或纠正误记可直接用原始来源，不伪造推进记录。图依然固定明确成员版本，共享节点的自动传播仍待单独确认；不能借本次存储设计悄悄改成所有图自动跟随最新版。

## 7. 完整保存事务及封存规则

服务先做不持锁的输入解析和初步检查，再进入短写事务：

1. 验证项目权限。按操作 ID 查成功结果；同请求则返回原回执，不进行下面的新增。
2. 使用写事务，在锁内再次核对项目基准；过期即冲突。插入 write_operations，结果版本由基准计算。
3. 插入新来源、业务身份、新修订和所有成员／来源／业务关联；核对类型、项目、时间及引用，更新变化对象的当前指针。同批新增对象可先分配稳定 ID，按依赖顺序插入或使用明确的延迟外键。
4. 检查至少有实际变化、所有新修订都有具体依据、图成员完整、状态依据有效、所有变化对象当前指针正确。
5. 插入 project_versions，封存本操作的修订、来源和关联集合。该行必须最后于内容及关联插入。
6. 将 projects.current_content_version 前进一版，核对它等于最新登记版本，并核对外键。创建项目时保持版本 0。
7. 提交事务，之后才返回成功回执。任何一步失败都回滚；服务进程中断也不能留下半次正式保存。

SQLite 的 BEGIN IMMEDIATE 用于先取得写事务，避免先读后升级造成歧义；忙锁应作为可重试错误处理，不能长时间持锁执行网络请求或生成文件。SQLite 同时只允许一个写事务，项目级版本规则不等于不同项目能无限并行写。[官方说明](https://www.sqlite.org/lang_transaction.html)

**只禁止 UPDATE／DELETE 还不够。** 每个修订表和来源表都要禁止给已登记的操作再 INSERT；每个成员表、来源引用表和业务关联表都要禁止给已封存的父修订再 INSERT。否则后来补一条图成员或依据，就能改变旧快照。

封存条件统一为“对应操作已出现在 project_versions”。约束分工：

| 层            | 检查内容                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------- |
| 数据库        | 主键、同项目外键、操作与登记版本一致、不可更新删除、封存后不可补行、合法头指针移动                  |
| 共同保存服务  | 至少一份依据及材料语义、无空保存、身份头等于最新修订、项目头等于最新登记、JSON 内部引用和完整图语义 |
| MCP／Web 入口 | 取得真实调用上下文并提交逻辑内容，不复制共同业务规则                                                |

不能声称 SQL 已自动保证所有业务完整性。尤其延迟外键只检查引用存在，不会自动执行“把当前头更新为最新”的语句。[SQLite 外键说明](https://www.sqlite.org/foreignkeys.html)

## 8. 失败和历史恢复

同一次提交的操作、版本登记、内容及来源共同事务保存：响应超时后，服务可根据操作 ID 找到稳定结果；不存在结果时可沿用原 ID 和载荷重试，不能仅凭一次查无结果认定旧请求绝不可能成功。

本地文件刷新发生在提交之后，失败不撤销数据库，也不新增另一份操作。网页和 MCP 修改都使用相同版本规则。

恢复旧内容时，以当前项目版本为基准，复制选定旧内容形成新修订，保留恢复说明和来源；项目版本继续前进。整项目恢复不是直接回退 projects 指针，也不是覆盖旧修订；其具体用户入口尚未设计。
