# 需求推进的数据模型

状态：**需求、记录、回顾及来源的正式存储和 MCP 已实现；需求和记录已接入只读页面。回顾专用页面等仍待实现。** 正式表结构以 migrations 为准，本文保留最初的逻辑模型推导；当前阅读行为见 [需求推进阅读](../requirements/requirements-reading.md)。 本文承接已确认的[需求与记录边界](../requirements/product.md)，与[项目及综述库表](project-overview-design.md)共用项目身份、保存操作和来源；不能把前八张表视为全系统库表。

## 1. 三个业务对象

```text
项目
├── 需求 A：一个能够独立讨论、推进和验收的目标
│   ├── 推进记录 1：明确了一项结论
│   └── 推进记录 2：后来取得结果，或改变了原决定
├── 需求 B
│   └── 推进记录 3
└── 阶段回顾
    ├── 核对了哪些原始材料和范围
    └── 保存了哪些结果：可同时涉及需求 A、B 及综述、设计
```

需求和记录的划分来自业务目标与结论，不从日期、聊天轮次、工具调用或回顾次数推导。一条推进记录有且只有一个主需求；一次回顾可以涉及多个需求，一个需求也可以被多次回顾推进。

## 2. 需求：当前要解决什么问题

| 信息                   | 建议内容                                                   | 保存位置                     |
| ---------------------- | ---------------------------------------------------------- | ---------------------------- |
| 需求 ID、项目 ID       | 稳定身份及隔离边界                                         | 需求身份表                   |
| 标题                   | 让人能快速识别目标                                         | 需求版本                     |
| 正文 Markdown          | 自然描述用户目标、范围和判断结果的依据，不强制拆成固定表单 | 需求版本                     |
| 当前版本号             | 指向当前需求描述                                           | 需求身份表                   |
| 创建时间               | 系统首次保存时间                                           | 需求身份表                   |
| 修改者、修改时间、来源 | 本次变化的执行信息和原始材料                               | 共用写操作、该版本的来源引用 |
| 状态                   | 已确定的六种状态；无不可逆终态，允许回退、恢复和跳转       | 需求版本                     |

后续补充范围或调整设计时，继续维护同一需求。只有形成可独立推进和验收的另一个用户目标时才新建需求。改标题不换 ID。

不提前增加优先级、负责人、估时、迭代、百分比进度、依赖审批等项目管理字段；目前没有已确认的使用需求。

### 需求状态

| 显示文案 | 结构中的值               | 含义                                                                 |
| -------- | ------------------------ | -------------------------------------------------------------------- |
| 设计中   | designing                | 需求理解、UI／交互和技术方案等必要设计仍在形成                       |
| 方案已定 | ready_for_implementation | 本需求所需的设计已足以支撑实现；不要求每项需求都有 UI 或独立架构文档 |
| 待验收   | pending_acceptance       | 已有完整实现结果，尚未核对是否满足约定要求                           |
| 已完成   | completed                | 已核对并满足约定的完成标准                                           |
| 暂缓     | on_hold                  | 当前决定暂时停止推进                                                 |
| 取消     | cancelled                | 当前决定不再做这项需求                                               |

状态是整个需求当前已经达到的阶段。方案已定可以覆盖其后尚未确认完整实现的设计调整和实现过程，具体活动由推进记录表达。状态不从工具调用、Agent 报告写完代码或一次回顾成功自动推断，也不设置默认值代替有依据的判断。

六个状态均可流转，不建立只能前进的转移表。每次真实状态变化生成需求的新版本，保留原因、来源及该版系统保存时间；修正错别字但状态未变时，不生成一条假的状态变化。当前状态变化时间从最近一次状态值改变的版本取得，而不是直接使用最近一次正文修改时间。共同历史要求见 [history-design.md](history-design.md)。

每次真实业务状态变化还要关联支撑它的一条或多条推进记录，并固定到具体记录版本，说明为何从原状态改为新状态。新增记录不自动推断状态；需要改变状态时，相关记录、状态版本及依据一起保存。记录属于同一项目并与该需求有关，关联与语义都要核对。后来修订记录不能悄悄替换旧状态变化的依据。

首次建立需求可直接关联原始来源；纠正误记状态也可引用更正依据，不必为了满足关联要求伪造新的业务进展。状态依据作为需求版本的关联保存，不混进正文或额外复制记录内容。

## 3. 推进记录：这项需求发生了什么变化

| 信息                     | 建议内容                                               | 保存位置                     |
| ------------------------ | ------------------------------------------------------ | ---------------------------- |
| 记录 ID、项目 ID         | 记录的稳定身份及项目归属                               | 记录身份表                   |
| 所属需求 ID              | 一个主需求；归类纠正时保留旧归属历史                   | 记录版本                     |
| 标题                     | 本条结论或结果是什么                                   | 记录版本                     |
| 正文 Markdown            | 自由段落，通常约 100～200 字；不强制字数或句式         | 记录版本                     |
| 实际发生时间             | 可确认时填写 UTC 毫秒时间；未知为 NULL                 | 记录版本                     |
| 当前版本号、首次记录时间 | 当前描述版本、系统首次收录时间                         | 记录身份表                   |
| 每版保存时间             | 这份版本实际保存到系统的时间，首版和每次修订都必须保留 | 该版本关联的写操作 saved_at  |
| 修改者、修改时间、来源   | 记录谁补齐或更正，以及来自哪里                         | 共用写操作、该版本的来源引用 |
| 关联旧记录               | 固定记录 ID及其具体版本、为什么关联                    | 版本化关联表                 |
| 对应的综述或设计内容     | 明确关联哪个对象和版本、为什么关联                     | 版本化内容关联表             |

正文标明事实、提议或待确认问题，不先假设存在一个已经定稿的“记录分类”枚举。关联旧记录时用说明表达承接、验证或推翻关系；当前不据一个链接自动推断“旧决定已失效”或“需求已完成”。

### 新增与修订

同一记录可有多个修订版本，`记录 ID + 版本号` 标识一份快照，记录身份指向当前版本。可以沿需求查看不同记录，也可以沿一条记录查看历次版本；时间线默认每条记录只出现一次，不把版本数当成进展数。两个方向是关联关系，不要求实现十字链表或为版本保存上下左右指针。

- 后来改了主意或取得新结果：新增记录。旧记录继续反映当时成立的结论，新记录引用旧记录的具体版本并解释变化。
- 摘要误记、遗漏、时间或需求归类写错：修订同一记录，保留记录 ID、前后版本和依据，不制造新的业务进展。
- 改写需求当前正文：形成需求的新版本；仅改错别字不必增加一条推进记录，但仍保留修订历史。
- 同一结果涉及多个独立需求：分别记录各需求自己的结论，可以引用同一来源和同一保存操作，不把它们硬塞进一个需求。

### 记录与版本各自有时间

实际发生时间回答“当时什么时候形成这个结论”，首次记录时间回答“什么时候被收录进 CoSeed”。每份版本都有自己的系统保存时间：首版的保存时间对应首次收录，此后每版的保存时间对应一次修订。

修订历史应逐版展示保存时间、修改者和来源；不能只在记录上保留一个会被覆盖的“最后修改时间”。每版通过自己的 operation_id 关联 write_operations.saved_at 取得保存时间，不把该时间写入正文或 occurredAt，也不要求所有版本分别增加一套重复的时间字段。同一批保存的不同对象可以具有相同保存时间，版本身份和顺序仍由所属对象及版本号确定。

实际发生时间在更正前后可有不同值，原值随旧版本保留；未知仍为 NULL。它既不会因为修订而自动变成“现在”，也不由版本保存时间补齐。示例文件中的 revisionTimeExample 使用明确标为虚构的时间演示两者的区别。

排序区分实际发生顺序和收录顺序。页面默认按首次收录的项目版本、同批次序倒序，最新收录在前；实际发生时间独立标注，修订不移动位置。一次回顾可能同时补入多条记录，保存时间相同不表示业务同时发生；已知的来源相对顺序也不能被随机 ID 的排序替代。后续物理模型须保留明确的收录次序，并按可核对材料表达业务先后；来源时间及顺序均未知时如实保留未知。修订同一记录不自动把它移动为一项新进展。

## 4. 阶段回顾：整理了哪些材料，保存了哪些结果

阶段回顾有独立业务身份，写操作表示一次成功提交；两者分开。数据关系不把它们锁成一对一，是否允许一次回顾分批保存仍待流程确认。一次保存也不必是回顾，例如用户直接修正综述。

建议先明确回顾的持久化信息：

| 信息               | 含义                                                                 |
| ------------------ | -------------------------------------------------------------------- |
| 回顾 ID、项目 ID   | 一次针对单一项目的整理工作，目标不随页面切换改变                     |
| 标题               | 这次回顾整理什么                                                     |
| 范围说明 Markdown  | 本次实际核对的讨论、仓库变化和边界                                   |
| 输入材料引用       | 使用了哪些已保存的来源片段；不同对话分别定位                         |
| 结果说明 Markdown  | 哪些内容已保存，还有哪些缺口                                         |
| 成功保存操作引用   | 关联本次实际完成的写操作，由此找到需求、记录、综述和设计的具体新版本 |
| 创建、修订及操作者 | 继续遵循身份、版本和共用来源规则                                     |

这里只定义回顾的内容和结果关系，**不把待执行、分析中、失败重试、自动续跑等运行状态当成已确认流程**。CoSeed 不因此成为 Agent 执行器；失败回顾和草稿怎样保留，仍需单独设计。

### 回顾范围与去重

- 输入引用说明“看过什么”；版本来源说明“依据什么修改了哪处内容”，二者不能互相替代。看过一整段对话不代表其中每条内容都支持本次所有结论。
- 成功结果从实际写操作及产生的版本关联得到，不另外保存一份“修改对象 ID 列表”当成另一套事实。
- 网络重试复用操作 ID，避免同一次提交重复保存；重新发起一次回顾，则需先查询已有需求、记录和已处理材料，再按稳定 ID归并或修订。
- 同一来源可以产生多个独立结论；同一结论也可以有多个来源。不能用“来源 ID 相同”或“文本相似”直接判定两条记录重复。
- 后一次回顾应能使用前一次实际完成的材料范围作为线索。来源的跨对话规范化尚未完成，当前不设计一个全项目“已处理到第几轮”的单一游标，也不宣称能自动识别所有语义重复。
- 已成功保存的部分有实际结果；尚未成功的范围不能标为完成。多批保存如何汇总成功和失败，需要回顾流程确认后再形成约束。

## 5. 与综述、业务设计如何关联

需要两类关联：

| 关联                                | 回答的问题                         |
| ----------------------------------- | ---------------------------------- |
| 需求 → 综述部分、业务模块等对象     | 这个用户目标覆盖项目的哪些内容     |
| 推进记录 → 具体内容版本、旧记录版本 | 这条结论对应哪里，当时看到的是什么 |

需求和记录均可建立必要关联，不能要求每次关联需求都先捏造一条推进记录。

综述已有内容结构，可用“综述版本号 + 对象种类 + 稳定 ID”定位概念、关系、用例或示例小节；产品表述等固定部分用明确的部分标识。历史引用固定版本，当前阅读入口再根据稳定 ID查找最新内容。若对象已删除，明确显示，不凭名称猜测替代对象。

关联到业务设计的目标类别，等业务设计 Schema 确定后采用真实关联表及外键；当前不建立任意 `target_type + target_id` 万能关系表。

跨项目、目标不存在、目标版本错误、对象种类不匹配均应拒绝。SQL 可验证关系对象和版本；JSON 内的稳定 ID及种类要由共同业务服务检查。某条记录是否真实导致一次设计变化，仍需要来源和关联说明支撑，不能只因为它们同批提交就推断因果。

## 6. 库表如何扩展

不改变现有八张表的模块边界。来源复用 `sources`，执行信息和提交重试复用 `write_operations`；需求与记录拥有各自身份和历史。

本批可先明确六张主干表：

| 表                               | 职责                                               |
| -------------------------------- | -------------------------------------------------- |
| requirements                     | 需求身份、项目归属、当前版本、创建时间             |
| requirement_revisions            | 需求标题和 Markdown 的历次快照，关联实际写操作     |
| requirement_revision_sources     | 该版需求具体部分的来源引用                         |
| progress_records                 | 推进记录身份、项目归属、当前版本、首次记录时间     |
| progress_record_revisions        | 当时的主需求、标题、Markdown、实际发生时间及写操作 |
| progress_record_revision_sources | 该版记录具体部分的来源引用                         |

记录属于哪个需求放进版本，纠正归类时不丢历史。需求时间线从当前记录版本筛选主需求；如果实测需要加速，可增加由事务维护并校验的当前关系投影，不让缓存成为第二个权威归属。

同一记录的版本不是时间线里的多个进展。列表读取身份的当前版本，修订历史单独读取。版本号只需项目内对象唯一且有明确顺序，不为“数字必须绝不跳号”再复制自引用链。

还需要按已明确的真实关系增加记录间引用、综述关联、回顾及输入／结果关联表。**六张主干表不是需求推进的完整物理表数。** 回顾的版本结构、分批保存边界，以及业务设计关联外键需与下一块模型一起收口，本次不提前固化全部 SQL。

## 7. 内容结构与存储信息分开

需求内容结构：`{ title, markdown, status }`。status 是已确认的六种值之一，不包含调用方编写的保存时间；版本时间由系统管理。

推进记录正文候选结构：`{ requirementId, title, markdown, occurredAt }`。这里只对文字和结构做校验，不把保存时间写进 occurredAt。

回顾内容候选结构：`{ title, scopeMd, summaryMd }`。原始材料和成功保存操作使用独立关联，避免复制来源正文和业务内容。它不是已经完成的回顾执行协议。

项目 ID、记录 ID、版本、执行者和系统时间由对应身份、版本和关联表维护，不混进每段正文。可执行候选见 [requirements-content-draft.ts](requirements-content-draft.ts)；[示例](requirements.example.json)用 CoSeed 自身的已讨论规则解释对象及“新增／修订”区别，不是生产数据或未来 MCP 请求格式。

## 8. 待确认事项与后续

- 六种状态及自由流转方向已确认；具体更新入口、来源提交和真实保存校验随业务流程落地，不从 Agent 编码结束自动判定完成。
- 时间线排序已确认：最新收录在前，补录旧决定作为新收录项，保留独立发生时间。
- 回顾的输入范围规范、草稿与失败保留、分批保存及续处理。
- 业务设计对象类别和双方真实关联结构。

需求、记录、回顾及其关联现已进入正式迁移和共同存储，MCP 已接入。当前需求只读页面复用这些模型；回顾专用页面、执行流程和远程权限仍需独立确认。物理结构与实际边界以 [数据库进度](README.md) 和 Architecture 为准。
