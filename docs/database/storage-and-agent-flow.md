# 数据库存储、本地资料目录及 MCP 读写流程

状态：**方向已确认，具体协议为设计草案，尚未实现。** 决策见 [ADR 0003](../adr/0003-database-and-agent-cache.md)。本文说明谁保存什么、资料如何到达 Agent、修改如何回到页面；不定义已经可调用的工具名，也不把下列目录当成业务数据库的文件格式。

## 1. 整体结构

```text
                    CoSeed 服务
                 ┌──────────────────┐
网页阅读／编辑 ────┤ 查询／共同保存规则 ├──── 数据库
                 │                  │     当前内容、修订、来源、保存操作
Agent ─── MCP ────┤ 快照导出／修改提交 │
  │              └──────────────────┘
  │ 拉取到本地；提交成功后刷新
  ▼
本地资料目录 ← Agent 直接读取、搜索
  读取副本，可删除重建

业务代码目录 ← Agent 正常开发、验证
  与资料目录分开；CoSeed 不接管源码写入
```

“通过 MCP 写”指提交 CoSeed 权威内容。初始化和刷新仍需要 Agent 写本地缓存；业务代码照常由 Agent 修改，不受此约束。

| 部分             | 保存或处理什么                                                     | 不承担什么                                   |
| ---------------- | ------------------------------------------------------------------ | -------------------------------------------- |
| 数据库           | 项目、当前资料、不可变修订、原始来源、关联、保存操作及项目内容版本 | 不要求同步另一套 Git 权威内容                |
| 共同业务服务     | 归属、Schema、引用、来源、版本冲突、原子保存、幂等结果             | 不因入口是 MCP 就跳过业务约束                |
| MCP              | 项目选择、固定快照读取、修改提交、保存结果和历史查询               | 远程服务不能直接写 Agent 所在机器的文件      |
| Agent 本地目录   | 一份固定项目版本的完整当前资料，方便读文件及搜索                   | 不是备份、修订历史库或待上传的第二套权威数据 |
| Agent 的文件能力 | 落盘、核对完整性、切换读取副本                                     | 不要求新增独立连接器                         |
| Web              | 读取数据库已提交的内容；编辑走共同保存服务                         | 不读取 Agent 电脑上的缓存                    |

## 2. 数据库保存什么

沿用已讨论的业务对象，先约定逻辑职责，物理表及字段仍以各模块后续定稿为准：

| 内容       | 存储语义                                                               |
| ---------- | ---------------------------------------------------------------------- |
| 项目及综述 | 稳定项目身份；产品表述、概念及关系、示例与对应图的当前内容和修订       |
| 需求       | 独立目标、当前正文及六种状态；每次真实修改保留修订                     |
| 推进记录   | 稳定记录身份、唯一主需求、正文、可知的发生时间；更正仍是同一记录       |
| 业务设计   | 节点、关系、图成员、技术说明及各自修订；身份与布局分开                 |
| 回顾       | 整理范围、输入材料、结果及成功保存操作的关联                           |
| 来源       | 原始片段、类型、定位和可知时间；后续解释更正不覆盖原材料               |
| 保存操作   | 操作身份、项目版本、保存时间、执行信息、入口、本次产生的修订和对应来源 |

完整 JSON 正文适合存为版本内容；需要跨对象校验和查找的关系使用明确关联。不是把整个项目塞进一份 JSON，也不把数据库内容强制拆成 Markdown 文件。

一次相关修改在同一个数据库事务中成立：新修订、来源、关联、当前指针、保存操作和项目版本共同提交；任一校验或写入失败，都不改变正式内容。

历史恢复仍产生新修订，保留恢复前的内容和恢复依据，不直接覆盖或删除旧历史。详细共同语义见[历史要求](history-design.md)。旧 SQL 草案不能未经复核直接迁移。

## 3. 三种版本分开

| 名称         | 作用                                           | 例子                                         |
| ------------ | ---------------------------------------------- | -------------------------------------------- |
| 项目内容版本 | 标识整个项目的一致快照；检查缓存过期和写入冲突 | 项目 P 当前为 24，一次有效保存后为 25        |
| 对象修订号   | 标识同一个对象的某次修订，供历史和固定引用使用 | 需求 R 的第 3 版；另一需求可能仍为第 1 版    |
| 导出格式版本 | 让客户端知道如何解释本地目录和清单             | 文件组织改变时处理格式兼容，不随正文修改增加 |

这些版本都由 CoSeed 的规则维护，不是业务 Git commit，也不是 CoSeed 程序的发布版本。

项目内容版本从 0 开始；新项目仍有名称等基本信息及初始化来源，但业务内容集合为空，不生成虚构需求或设计。每次成功改变可导出内容的事务增加一次，失败、读取、缓存刷新和没有实际变化的重试不增加。项目 A 的版本与项目 B 无法比较；版本不是时间戳。

各对象修订关联产生它的保存操作，操作关联唯一项目内容版本。因此能重建“项目版本 24 时各对象分别是哪一版”，不需要每次复制整个数据库。删除或归属变化也须留下可重建的历史，不能只保留当前指针。具体操作字段、历史查询及封存规则见[共同模型提案](snapshot-save-model.md)。共同层、项目／综述和图 SQL草案已组合验证，尚未转为正式业务迁移；保留策略和容量仍待验收。

当前图按当前项目快照解析节点、关系、说明及归属；历史图按指定历史项目快照解析。图中只存稳定成员 ID，共享节点内容更新不复制图清单修订。所有受影响的当前图必须在同一候选快照中合法，否则整批拒绝；详见 [ADR 0004](../adr/0004-operation-snapshot-resolution.md)。

## 4. 本地资料目录

推荐在业务仓库外选一个 Agent 可读写的缓存根目录，按 CoSeed 服务身份及项目 ID 隔离；服务身份不能仅靠项目名称区分。绝对路径由 Agent 所在环境决定，并告知使用者。业务仓库内也不强制提交这些文件。

下面是**读取布局草案**。文件以稳定 ID 定位，标题变化不改变身份；目录和扩展名不是 MCP 写入格式。

```text
<cacheRoot>/<serviceId>/<projectId>/
├── current/                     # 当前已完整拉取的一个快照
│   ├── manifest.json            # 项目、版本、完整文件清单及校验信息
│   ├── overview/
│   │   ├── product.md
│   │   ├── concepts.json
│   │   └── examples/            # 背景、角色、用例、小节正文及图数据
│   ├── requirements/<id>.json   # 标题、状态、正文等统一逻辑内容
│   ├── records/<id>.json        # 包含主需求、正文和发生时间
│   ├── design/
│   │   ├── entities/<id>.json
│   │   ├── relationships/<id>.json
│   │   ├── diagrams/<id>.json
│   │   └── notes/<id>.json
│   ├── retrospectives/<id>.json
│   ├── history/                 # 当前引用所需的固定旧修订，不是全历史
│   └── sources/<id>.json        # 当前内容实际引用的原始材料
└── staging/<downloadId>/        # 尚未完成的下载；不作为正式读取入口
```

不再为 Git diff 制定 JSON 元数据加 Markdown 正文的强制拆分协议。上述 JSON 可直接包含 Markdown 字符串；综述等长篇阅读材料可以生成 Markdown 视图。具体导出字段、正文阅读形式和格式版本下一步定稿，必须能还原全部逻辑内容，不能只导出摘要或截断的卡片文字。

清单至少声明：服务身份、项目 ID、项目内容版本、导出格式版本、快照标识、内容文件总数，以及每个内容文件的相对路径、字节数、SHA-256 和对应对象／修订。字节数及哈希针对实际导出的 UTF-8 字节；文件清单不包含 manifest 自身，避免自引用哈希。相对路径不能越过缓存目录；不接受绝对路径、`..`、重复路径或符号链接覆盖。清单由服务生成；客户端以它确认完整性，不通过“数起来差不多”判断完成。

本地文件不包含 MCP 凭据。来源中本来存在的敏感材料也不能因为导出就向无权限者公开；项目读取授权和来源可见范围仍须在正式认证设计中落实。

“完整当前资料”包括综述、所有需求和所有推进记录的当前修订、全部当前设计内容、回顾结果，以及引用闭包中必要的原始来源和固定历史对象。已完成、暂缓、取消的需求不因此省略。历史引用需要的旧对象以清单标明的独立历史区域导出，不能冒充当前对象覆盖同一路径；具体历史子路径随导出格式定稿。

这不表示默认下载每个对象的全部历次修订或所有未引用的原始材料；完整修订历史经 MCP 按需查询。若未来需要全历史离线包，应单独明确范围，不能把当前包称为全历史备份。

## 5. 初始化：把资料完整拉到本地

1. Agent 连接 MCP，明确选择 CoSeed 服务和项目 ID，不从目录名猜测。
2. 服务确定一个项目内容版本，例如 24，并生成绑定该版本的快照清单。
3. Agent 按清单通过 MCP 分批拉取内容，使用自己的文件能力写入 `staging/<downloadId>/`。
4. 每一批固定同一快照；下载期间数据库即使更新到 25，剩余文件仍来自 24，不能混入新内容。
5. 文件完整、校验通过后，Agent 将这份快照设为本地 `current`，明确当前读取的是版本 24。切换过程不能让读取者看见半新半旧的目录；同项目的缓存更新须串行。具体目录切换实现在客户端流程定稿时验证。
6. 确认完整拉取后，Agent 读取与本次任务相关的正文和图数据。已下载不等于模型已全部阅读、理解或永久记住。

服务应从一致的数据库读取快照生成不可变导出结果，再分页传输；不能为了等待 Agent 的后续调用一直持有长数据库读事务。导出结果可使用可重建的临时缓存，但权威内容仍在数据库。

下载中断时，不替换当前有效副本。允许在快照仍有效时续传；快照过期则重新开始一次完整下载，不拿新快照续接旧文件。保留时长、清单分页及传输大小限制仍需具体契约。

新项目也走同一流程，明确返回“尚无资料”，不生成虚构需求、来源或设计节点。

## 6. 日常读取：以本地文件为主

开始新任务、恢复会话时，Agent 先向 MCP 查询项目当前版本：

- 与本地版本相同：直接读本地资料、搜索和定位。
- 不相同：刷新完整副本，读取变化后再继续，不假定原来的理解仍成立。
- 服务不可达：可以阅读已经完整下载的旧快照，但须标明版本和过期情况；不能据此宣称读取了最新内容。

第一版优先采用完整刷新，复用清单和下载流程；是否增加增量下载由实际容量和性能决定，不先建设一套双向同步算法。

本地缓存删除后重新拉取即可。文件被误改时可通过清单哈希发现并重新下载；这些改动不会成为 CoSeed 的正式修改，也不支持在离线目录里积累修改后自动合并上传。

“只读副本”首先是数据职责约定。仅靠提示词不能证明目录在操作系统层面不可写；Agent 初始化和刷新本身也需要写缓存。权限隔离是否额外实施另行决定，系统保证的是绕过保存服务修改缓存不能改变数据库。

## 7. 推进任务及整理修改

Agent 结合本地资料和实际业务代码开展工作，正常修改源码并验证；用户明确发起回顾或资料同步时，再整理本次相关变化。不把每次代码编辑自动变成推进记录。

整理时区分：新结论产生新记录，纠正误记产生原对象的新修订；需求状态变化有实际依据；综述或设计有影响才更新。具体内容沿用各模块的内容 Schema，不用文件差异替代业务判断。

Agent 准备的是一组**逻辑对象修改**及来源，例如需求、记录、节点和关系。它无需先编辑读取副本，不提交任意文件路径或整个目录覆盖指令。

业务代码对应关系单独保存：资料依据的仓库、代码提交或尚未提交文件的实际内容标识。项目内容版本 24 只定位 CoSeed 资料，不能代替业务代码版本，也不能证明用户工作区没有后续变化。服务不会替 Agent 扫描远端机器的磁盘。

## 8. MCP 提交：一次保存共同成立

提交至少需要表达以下含义；这是概念契约，字段及工具名尚未注册：

| 信息                           | 谁提供                                                     |
| ------------------------------ | ---------------------------------------------------------- |
| 目标项目 ID                    | Agent 明确选择，服务检查权限和项目归属                     |
| 基准项目内容版本               | Agent 提供本轮实际读取的版本，例如 24                      |
| 本次操作标识                   | 调用前确定，超时重试保持相同；具体分配方式在工具契约中定稿 |
| 新增／修订的逻辑内容及相关引用 | Agent 整理，服务按类型和跨对象规则检查                     |
| 原始来源及其支持的具体修改     | Agent 提供；网页人工编辑由共同保存服务保留原始输入         |
| 对应回顾及业务代码上下文       | 有实际材料才提供，不伪造时间和代码状态                     |

服务处理顺序：

1. 确认项目权限和操作身份，检查操作标识是否已经成功保存。
2. 解析内容，校验 Schema、身份、来源、归属、图端点及引用；明确受影响的当前图。
3. 在数据库事务中重新检查基准，预定操作 ID，先保存来源、新修订和关联，并校验完整候选快照。必须防止“校验之后、保存之前”发生并发覆盖。
4. 校验通过后最后插入成功保存操作，封存本次内容集合，更新当前指针，将项目版本从 24 增加到 25。
5. 事务提交后，返回成功结果：操作标识、新项目版本、受影响对象及其修订。实际保存时间和已知身份由服务记录，不让 Agent 伪造。

第一版使用项目级冲突检查：即使两次修改碰巧涉及不同对象，只要基准过期，也先拒绝并要求重新核对。它较保守，但规则清楚；细粒度自动合并以后按实际需要设计。

有依赖的一批变化不能按文件逐个正式保存。超出当前 1 MiB 请求限制时，需要暂存后整批校验和提交的契约，或由调用方拆成各自合法、可独立理解的批次；具体方式尚未确定。不能直接假定一个无限大的提交可调用成功。

网页编辑遵循相同规则，包括基准版本、来源和事务；Agent 的本地副本不会因为网页编辑自动变新，仍在下次检查时刷新。

## 9. 保存之后：分别确认数据库和本地副本

```text
MCP 保存成功 → 数据库已是版本 25 → Web 可查询版本 25
          └→ Agent 拉取最新完整快照 → 切换本地副本
```

数据库保存成功后即可确认正式内容已更新，不再经过 Git 保存、异步索引、另一次页面发布的三段过程。页面仍需重新查询数据；浏览器没有刷新不是数据库尚未保存。

本地刷新优先取得最新快照；若另一操作已将项目推进到 26，可以直接完整下载 26，但本次保存回执仍明确是 25。不能把本次保存结果改称 26，也不能把旧缓存直接改个版本号冒充刷新。

若本地刷新失败，报告“已保存到版本 25，本地副本尚未刷新”，保留旧副本的真实版本；之后只重试下载，不重新提交同一组新增记录。后续准备修改前必须重新核对最新内容。

## 10. 冲突和失败怎样恢复

| 情况                           | 结果及后续动作                                                             |
| ------------------------------ | -------------------------------------------------------------------------- |
| 下载缺文件、校验失败或连接中断 | 保留上一份完整副本；重试同一有效快照或重新下载                             |
| 导出快照过期                   | 重新取得清单和固定版本，不混用前后批次                                     |
| 内容或来源校验失败             | 不保存；保留待提交内容，按具体错误补齐                                     |
| 基准 24、服务已是 25           | 不覆盖；重新拉取，阅读并核对差异后再准备提交，不能只把基准数字改成 25      |
| 提交响应超时，不知道是否成功   | 按操作标识查询结果；也可用相同标识和相同逻辑载荷安全重试，不盲目创建新操作 |
| 同一操作标识重复、内容相同     | 返回原成功结果，不再次产生修订、记录或项目版本                             |
| 同一操作标识重复、内容不同     | 明确拒绝，不复用旧结果冒充新修改已保存                                     |
| 数据库事务失败                 | 整批回滚，旧正式内容保持有效；没有成功回执不能宣称已经记录                 |
| 保存成功、本地刷新失败         | 保留成功回执，只补做刷新；Web 可查询已保存结果                             |

幂等结果与成功操作、正文在同一事务中保存，不能只放在进程内存；进程重启后仍能确认结果。操作标识查询暂时无结果也不自动证明前一请求从未执行，重试仍须沿用原标识。重复操作的检查应能返回旧成功结果，而不是先按过期基准拒绝已完成的重试。

## 11. 历史和当前资料怎么对应

- 当前阅读按稳定对象 ID 定位；历史读取明确指定对象修订，不悄悄替换成最新版。
- 一条推进记录被修订多次，当前时间线仍是一条记录；历史入口展示各次修订及保存时间。
- 状态变化依据的推进记录固定到当时修订；后续更正不改写旧依据。
- 同一次保存可以修改多个对象，它们共享保存操作及项目版本，各自保留具体来源。
- 真实业务发生时间、系统保存时间及本地下载时间分别表达；未知发生时间不由下载时间补齐。

“把当前资料完整拉到本地”和“服务器保留全部历史”是两个职责。数据库及备份保护历史，本地缓存方便 Agent 理解现状。

## 12. 当前实现与后续验收
