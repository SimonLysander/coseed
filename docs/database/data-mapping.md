# CoSeed 数据如何从提交变成页面

状态：**数据库及内部共同保存服务已实现；图中 MCP、页面与本地文件导出部分仍待接入。** 完整操作流程见[存储及 Agent 读写](storage-and-agent-flow.md)，版本规则见[保存模型](snapshot-save-model.md)。

## 1. 两种数据不要混淆

CoSeed 保存的是综述、需求、推进记录、设计对象、连线、图、来源和修订。图里出现的 Account 等 TS 类型是被描述项目的数据结构文本，不表示 CoSeed 替业务项目创建数据库表或保存真实账号。

## 2. 整条数据流

```text
用户明确发起回顾／同步
  → Agent 结合讨论、实际代码及本地资料，整理逻辑修改与原始依据
  → MCP 提交项目、读取基准、本次操作 ID、内容及来源
  → 共同保存服务核对结构、项目、旧版本、引用和完整候选图
  → 同一数据库事务保存身份、新修订、关联、来源
  → 最后保存 write_operations，形成新项目版本并封存
  → 更新当前指针并提交
  ├→ Web 查询数据库已提交内容，组装页面
  └→ Agent 拉取完整固定快照，刷新本地读取副本
```

内容 Schema 不接受 Agent 伪造的系统保存时间。服务器保存实际入口和可获得的身份；MCP 本身不自动提供完整原始对话。

## 3. 逻辑对象如何落库

| 内容               | 主体数据及对应表                                                         |
| ------------------ | ------------------------------------------------------------------------ |
| 项目基本资料       | projects 身份及 project_revisions 中的名称、可选仓库定位                 |
| 综述               | project_overviews 身份、overview_revisions 的完整 content_json           |
| 需求               | requirements、requirement_revisions 中的标题、正文、六种状态             |
| 推进记录           | progress_records、progress_record_revisions 中的主需求、正文、发生时间   |
| 回顾               | retrospective 身份、修订、来源及成功操作关联；完整 SQL 已纳入正式迁移    |
| 设计节点           | business_entities、business_entity_revisions 的分型内容                  |
| 设计关系           | business_relationships、business_relationship_revisions 的端点和语义内容 |
| 图                 | design_diagrams、design_diagram_revisions，三张稳定 ID成员表             |
| 技术说明           | technical_notes、technical_note_revisions，说明成员表                    |
| 来源               | sources 原文；每类修订的真实来源关联                                     |
| 成功保存及项目版本 | write_operations；没有额外 project_versions 表                           |

业务模块分别维护各自字段。结构化正文可为 JSON，真实关联使用类型明确的关系表；没有万能内容表或全项目大 JSON。需求／回顾完整 SQL 和跨模块关联已在正式迁移定义，由应用启动迁移；页面和 MCP 的调用仍待接入。

## 4. 修改一个共享节点

假设项目版本为 24，两张图都引用“需求更新处理”这个稳定 ID；节点当前修订为 1，图清单均为修订 1。

```text
保存前
  项目版本 24 → 图 A / 清单 1、图 B / 清单 1 → 节点修订 1

一次保存
  节点增加修订 2，关联本次来源和预定操作 ID
  图成员未变 → 不制造图清单修订
  核对所有受影响当前图仍合法
  最后保存操作：基准 24 → 结果 25

保存后
  读取项目版本 25 → 两张图均解析节点修订 2
  读取项目版本 24 → 两张图仍解析节点修订 1
```

若关系改到了图外的新组件，不能只因为新组件存在就保存。必须把相关图成员一起改正确；有一张未编辑图仍不合法，整次保存回滚。

图的 owner、外部系统名称、连线及技术说明都按同一项目版本解析。不固定 owner_revision_no，也不为每次共享内容变化复制多份图。图历史入口必须带项目版本，单独的图修订号只定位成员清单。

## 5. 数据如何呈现

| 业务信息                               | 页面呈现                                 |
| -------------------------------------- | ---------------------------------------- |
| 节点 kind、name、summary               | 对应卡片、名称、职责                     |
| typeName、typeScript                   | 带行内注释的 TS 结构，不执行文本         |
| owner、图 scope                        | 计算模块边界内外，归属名称按项目快照取得 |
| 核心实现来源路径                       | 目录分组，不在节点正文重复存路径         |
| 关系 kind、summary、operations／events | 线型、箭头、业务说明、语义函数式标签     |
| 关联字段及端点数量                     | UML 基本关联标记，绑定真实端点           |
| 技术说明及成员                         | 技术名称、解决问题、语义圈选范围         |
| 全局 Token及实际文字尺寸               | 字体、配色、间距；ELK 自动布局，X6 呈现  |

不将主题、坐标、缩放、路由或 X6 cells 当成业务权威内容。布局或派生缓存不能改变对象身份与归属。

## 6. 综述和需求推进

综述版本保存 product、concepts、examples；页面分别呈现产品表述、概念关系、示例背景和每节用例图及正文。内部对象使用稳定 ID；历史证据链接须指定综述修订及内部对象，不能按小标题猜测。

当前需求和记录按所读项目版本取得每个对象当时最后有效修订。记录更正多次仍是一条记录；后来形成新结论才新增记录。状态历史只显示真正的状态变化，支撑它的记录固定具体修订，不随记录后续更正变化。

发生时间来自材料，未知为 NULL；保存时间来自操作。本地下载时间不代替业务发生时间。

## 7. 当前完成边界

共同 SQL、项目／综述 SQL和图 SQL可组合验证；内容 Schema和图样例已按稳定成员更新。验证使用临时数据库，不是实际运行的保存服务。
