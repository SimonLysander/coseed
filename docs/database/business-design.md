# 业务设计的数据模型

状态：**内容结构及物理 SQL 提案；已在临时数据库验证，未迁移、未接入图形页面或业务接口。** 本文沿用已确认的两层图，参考已安装的 X6 3.1.8、React 节点适配包 3.0.1 和 ELK 0.12.1，不把历史原型中的过期节点模板重新当成当前规则。

[数据示例](business-design.example.json)全部是 CoSeed 的设计意图示例，不表示业务模块或调用接口已经实现。[可执行校验草案](business-design-draft.ts)分别定义对象、关系、图和技术说明；集合 bundle 仅用于校验引用，不是未来 MCP 的写入格式，也不建议把整个项目一次存成一块 JSON。

## 1. 四类需要分别维护的内容

| 内容     | 保存什么                                           | 为什么分开                                             |
| -------- | -------------------------------------------------- | ------------------------------------------------------ |
| 业务对象 | 业务模块、处理组件、数据对象及外部系统的身份与描述 | 多张图可引用同一个对象，避免各图复制一份定义           |
| 业务关系 | 两端对象、关系含义、调用／读写／关联等具体内容     | 同一关系可以在多图使用，修改与来源可独立追溯           |
| 设计图   | 观察范围，以及采用的对象、关系、说明的稳定 ID      | 图表达一个明确问题，历史图必须能还原当时内容           |
| 技术说明 | 技术名称、解决的问题，以及覆盖哪些对象             | 单节点或多节点范围都能承载策略，不新增独立技术设计页面 |

对象身份与图上的位置分开。同一个对象在不同图中使用同一身份；一张图内不重复画出两个无区别的同对象节点。原型中的组件、业务对象、目录区域和技术圈选不是四种并列业务对象。

## 2. 对象的内容结构

| kind            | 对象     | 内容                                                                          |
| --------------- | -------- | ----------------------------------------------------------------------------- |
| module          | 业务模块 | 名称、职责摘要、核心／支撑角色                                                |
| component       | 处理组件 | 名称、较详实凝练的职责摘要、唯一归属、可用时的核心实现来源                    |
| data_object     | 数据对象 | 名称、简短含义、唯一归属、TS 类型名和带行内注释的核心结构、实现及字段定义来源 |
| external_system | 外部系统 | 名称、说明；作为外部部件的归属范围或全景中的外部参与系统                      |

处理组件和数据对象的 owner 明确引用本项目业务模块或外部系统。**“在边界内／外”由当前图的观察范围和对象归属计算，不是对象自身永久写死的 external 标记。** 属于另一个业务模块的组件，在本模块内部图中是外部协作者；进入其所属模块后则是内部对象。

没有源码的设计提议允许实现来源为 NULL，不编造路径。已有实现的目录分组由核心实现来源的仓库相对路径推导，辅助来源不导致重复归属；字段定义可以来自另一份来源，不改变核心目录归属。源材料应属于同项目、类型及定位有效，并成为该对象版本的实际引用。

处理组件不强制展示方法、类、CRUD 或规则清单；数据对象直接展示核心 TS 字段。40～70 字等阅读建议属于写作与测量规范，不设置成结构校验的硬字数门槛。Schema 不执行 TS 文本，也不能证明摘录就是代码事实。

## 3. 两层图

### 业务全景

观察范围是整个项目。图内主要是同层级业务职责模块，必要时引用外部系统；依赖线表达履行职责需要谁的能力，无向关联线表达具体业务联系。它不把操作步骤、技术设施和数据结构混成同层模块，也不把依赖方向当输入输出顺序。

### 模块内部

scope 明确引用一个业务模块的稳定 ID，具体描述按所读项目快照解析。图的基础节点是处理组件与数据对象；本模块的对象放在边界内，其余对象放在边界外。目录是代码归属形成的区域，技术说明范围是语义成员集合，两者分别建模。

节点直接展示名称、职责或数据结构；两层均沿用无 Hover 的方向，内部节点暂不激活或展开。是否下钻由明确图引用决定，不自动生成不存在的下一层；本提案不增加第三层代码页面。

图保存：title、scope、entityIds、relationshipIds、noteIds。成员只引用稳定 ID，所有内容按同一个项目版本解析；图中不得出现没有对应对象的连线端点或超出选中对象的技术说明。partial 图的职责是否完整、是否正交仍需审阅；引用合法不等于业务已经完整。

## 4. 关系的内容

| kind                  | 两端                                     | 保存与直接显示的含义                                           |
| --------------------- | ---------------------------------------- | -------------------------------------------------------------- |
| functional_dependency | 模块／外部系统之间，至少一端为本项目模块 | 依赖什么业务能力；箭头由依赖方指向提供方                       |
| module_association    | 模块／外部系统之间，至少一端为本项目模块 | 具体业务联系，无箭头                                           |
| call                  | 组件 → 组件                              | 业务说明；逐项动作、核心输入、返回含义；已知时保留实际接口签名 |
| read                  | 组件 → 数据对象                          | 业务说明；读取动作、查询依据、读取内容                         |
| write                 | 组件 → 数据对象                          | 业务说明；写入动作、定位依据、修改内容                         |
| object_association    | 数据对象之间                             | 业务说明、关联字段和两端数量，无箭头                           |
| event                 | 发布组件 → 订阅组件                      | 业务说明；逐项事件名称、事件标识与核心载荷                     |

字段按关系类型区分，不接受把返回内容塞进读写关系，或把调用签名塞进事件。未知接口、返回或数量明确为 NULL，不能伪装成“无返回”或猜测 `1 — 0..*`。这扩展了旧原型只接受已确认返回性质的限制，尚需图形接入时设计“待确认”的具体呈现。

固定箭头、线型和 UML 标记从 kind 生成，不重复保存 kind、stereotype、umlRelation 三套可能相互矛盾的含义。两端数量分别绑定真实端点，布局改变不会交换它们；数量说明历史数量还是同一时点约束，仍需业务文字和来源交代。

调用显示“动作（核心输入）：返回含义”，读取显示“读取动作（查询依据）：读取内容”，写入显示“动作（定位依据；修改内容）”，事件显示“事件（核心载荷）”。完整业务说明仍保留；返回数据不另画一条反向调用。图借用 UML 基本关系，不声称实现完整 UML 元模型。

## 5. 技术说明

内容为 title、problemMd、entityIds。技术名称可以是状态机、事务边界、策略模式等；problemMd 解释解决什么问题并融入选择理由，不增加模板化的“为什么”区，也不要求凑齐一套技术主题分类。

entityIds 可以只有一个对象，也可以覆盖一组对象。不能把设计范围直接存成矩形坐标或作为所有对象的 parent；多个说明的语义范围可能重叠。呈现层必须准确表达成员，不能为画一个矩形把无关节点圈进去，或通过复制节点改变目录归属。

## 6. 与前端库如何对应

| 业务信息                         | X6 负责                  | ELK／适配层负责                                |
| -------------------------------- | ------------------------ | ---------------------------------------------- |
| 处理组件、数据对象               | React 节点卡片及交互命中 | 按全局字体与实际内容测量尺寸                   |
| 模块边界、目录树                 | 父子 cell 分组           | 生成 compound children、计算嵌套几何并转换坐标 |
| 功能依赖、调用、读写、关联、事件 | edge、标记和 labels      | 正交路径、端口、标签位置及端点映射             |
| 关系说明、语义操作、两端数量     | 多标签显示               | 文字尺寸预先计入布局，分别绑定端点             |
| 技术说明的成员范围               | 独立注释覆盖层           | 范围布局或无歧义轮廓；不能篡改唯一父分组       |
| 缩放、平移、点选与主题           | 页面会话和图形视图状态   | 与业务内容和历史分开                           |

X6 支持 React 节点、父子分组、端口、边路径和多标签；ELK 支持嵌套节点、端口、标签及边分段，但通常不会替应用测量中文文字。**能力与类型已核对，完整业务图尚未迁入 X6，不把文档能力当成集成验收。**

X6 序列化数据包含 shape、attrs、几何及视图配置，可以用于派生缓存或导出，不作为业务内容的权威存储。适配时给 cell 使用可还原的命名空间，避免对象 ID和关系 ID在 X6 单一 cell 集合中冲突。

业务内容 → 版本解析与图投影 → 字体／卡片测量 → ELK → 坐标和端口转换 → X6。ELK 已给出路径时，X6 不再独立重算同一条线。布局缓存按图及引用内容版本、算法配置和字体尺寸条件识别；主题只改颜色时不必改写业务或历史。

颜色、字体、间距和动效继续来自全局设计系统，不进入对象内容。需要用现有完整模块图验证目录嵌套、外部对象、说明范围、TS 字段、端点数量、所有关系与长标签，之后才可宣称满足呈现和性能要求。

## 7. 身份、历史与当前内容

四类内容各有稳定身份和修订，执行者、保存时间及来源复用[历史规范](history-design.md)。当前图按当前项目版本解析；历史图固定历史项目版本，不能混用今天的节点或归属名称。

图清单只保存成员 ID。共享节点、关系或说明变化后，引用它的当前图在新项目快照中采用新的有效内容，不为传播变化复制图修订。只有成员、观察范围或图标题发生变化才修订图本身。图修订号只标识清单，完整历史图用项目 ID、图 ID及项目版本定位。

保存时必须校验完整候选快照中的受影响图：端点变更、说明范围变化、对象移除或归属变化不能使未直接编辑的图失效。必要关联修改一起保存，任何图不合法就整批拒绝。此规则已在临时 SQL 实验验证，尚未接入业务服务；真实规模的增量检查和性能另行验收。

原型直接把对象内容嵌进每张图的模型适合独立展示；正式系统需要先明确对象身份与引用，不能把不同图中的同名卡片直接当成不同业务对象，也不能仅凭名称自动合并。

## 8. 库表边界及关联

业务设计内部可采用有明确种类的对象登记表，限定为本模块的四种设计对象，并使用对应的严格内容 Schema；它不是存放需求、综述及任意插件内容的万能表。

主干身份／版本对：business_entities / business_entity_revisions、business_relationships / business_relationship_revisions、design_diagrams / design_diagram_revisions、technical_notes / technical_note_revisions。另有四张成员关联表、四张版本依据表，共新增 16 张物理表，复用已有项目、来源与保存操作。完整字段、复合外键、索引及约束边界见[物理库表提案](business-design-tables.md)和[可执行 SQL](business-design-schema-draft.sql)。图及归属采用稳定身份引用，按所读项目快照解析；记录依据等固定历史引用仍明确具体修订。

需求关联业务模块或设计对象；推进记录关联其具体版本；设计内容也能反查相关需求与记录。项目归属、对象种类和目标版本均需检查。第一层模块与第二层同一模块边界共用对象身份，目录路径不替代身份。

本模块已补齐物理 SQL 草案并用现有设计示例验证内容往返和历史引用。下一步仍须收口需求推进／回顾的完整物理表及跨模块关联、来源规范和实际规模性能，然后才转换为正式 Drizzle 和迁移。整条数据映射见[提交到页面](data-mapping.md)；尚未执行个人数据库迁移或变更页面。
