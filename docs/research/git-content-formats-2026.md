# CoSeed Git 资料格式与索引方案调研

核对日期：2026-11-06。状态：**备选方案研究，已不作为当前实施方向**。后续用户决定先不用 Git，改为数据库权威存储及 Agent 本地读取副本，见 [ADR 0003](../adr/0003-database-and-agent-cache.md)。下文保留当时的调研、实验和推荐，不作为当前协议。没有修改运行时存储、生产依赖、业务 Schema 或执行数据迁移。

## 1. 结论

Git 中保存可解析的内容文件，再建立数据库查询索引，有直接先例。应复用这套分工，但不能因此认为某个 CMS 的字段、目录、权限或发布规则可以直接覆盖 CoSeed。

对当前 CoSeed，推荐 **结构化内容用 JSON，自由 Markdown 正文独立保存**：

- 节点、连线、图清单、概念关系、稳定 ID、状态等使用严格 JSON。
- 需求正文、推进记录正文等自由文字使用 `.md`；同一对象的元数据使用 JSON。
- 简短名称、职责、参数说明等仍留在 JSON，不按字符数自动拆文件；哪些字段是正文由格式规范固定定义。
- MCP 对外仍是统一的结构化对象，服务负责序列化和还原。Agent 不需要直接管理资料 Git 仓库，也不必安装连接器。

这是一项基于产品目标和实验的**推荐**，不是行业强制标准。全 JSON 仍是可行备选：它最简单，但自由正文的 Git 行级差异可读性较差。混合格式增加了同一对象多文件一致性检查，需要在正式协议中明确。

## 2. 前提来自当前项目

当前已经确认：Agent 通过原生 MCP 客户端直接连接 CoSeed；Git 保存资料及历史，数据库保存服务元数据和查询索引；业务仓库无需放入 CoSeed 文件。读写入口包括 MCP 和后续网页编辑。

现有内容 Schema 草案已经区分结构化字段与自由 Markdown 字段，相关位置：

- [综述内容](../database/overview-content-draft.ts)：产品表述、概念、示例及其正文。
- [需求推进内容](../database/requirements-content-draft.ts)：需求标题、正文、状态；推进记录的主需求、正文、发生时间。
- [业务设计内容](../database/business-design-draft.ts)：对象、关系、图清单、技术说明。

这些是业务内容草案，不是已经确定的 Git 文件格式。尤其旧草案中的对象修订号引用，不能不加调整就与 Git 提交并列作为两套权威历史。

当前已有 JSON 标准能力、Zod 和 markdown-it，可用于结构解析、逻辑校验和显示。`markdown-it` 负责显示 Markdown，不负责决定需求字段或跨对象关系。本文没有引入 CMS 框架。

## 3. 已确认的先例

### TinaCMS：内容源与查询层分开

官方 Data Layer 说明：Markdown／JSON 文件是内容依据，数据库为解析后的内容、查询元数据及文档引用提供索引，API 查询可使用索引数据。不同部署方式的索引触发有差异，不能把云端 webhook 更新方式当成自托管服务的普遍保证。[Data Layer](https://tina.io/docs/reference/content-api/data-layer)

其 collection 约定路径、格式和字段。底层源码分别处理 Markdown frontmatter、JSON、YAML 等格式，再映射为逻辑数据，写入时按所选格式序列化。这说明接口对象与物理文件无需完全一致。[Collections](https://tina.io/docs/reference/collections)、[解析和序列化源码](https://github.com/tinacms/tinacms/blob/main/packages/%40tinacms/graphql/src/database/util.ts)

CoSeed 可借鉴：独立 codec 层、结构 Schema 和索引层。TinaCMS 的网站内容模型不直接解决需求状态变化、原始证据和多对象提交的业务规则。

### Backstage：可升级的结构化对象格式

Backstage 的文件使用 YAML，接口使用 JSON，但共享相同结构和语义。它通过 apiVersion、kind 等字段判断对象格式；元数据与对象内容有明确边界。[Descriptor Format](https://backstage.io/docs/features/software-catalog/descriptor-format/)

资料进入目录后还经过校验、处理和最终拼装，最终可见对象与原始输入不同；不能只把文件读取成功当成完成发布。[The Life of an Entity](https://backstage.io/docs/features/software-catalog/life-of-an-entity/)

CoSeed 可借鉴：版本化解析、对象种类、处理后再发布，以及源内容和派生结果的边界。它的组件、资源和组织模型不等于 CoSeed 的需求和设计模型，解析器不能自动证明业务拆分正交完备。

### Decap CMS：元数据与 Markdown 正文合成一个文件

Decap 规定 collection 的解析与写入格式，支持 JSON、YAML 和带 frontmatter 的正文；body 字段对应前置信息之后的文本。明确配置 format 能避免只凭扩展名推断规则。[Configuration Options](https://decapcms.org/docs/configuration-options/)

这是“一个 Markdown 文件同时保存元数据和正文”的成熟先例。CoSeed 如选此路线，仍须明确前置信息格式、允许字段、值类型及文本规范，而不是手写正则解析 YAML。

### Keystatic：结构字段与正文可以分文件

Keystatic 默认把结构字段写入 YAML，并可将内容字段另存为 Markdoc／MDX 文件；也提供单文件 frontmatter 方式及 JSON 数据格式配置。这证明“一个逻辑对象拆成结构文件和正文文件”有现成设计先例。[Format options](https://keystatic.com/docs/format-options)

CoSeed 可借鉴文件分离的思路，正文仍使用目前已有的普通 Markdown，不因此引入 Markdoc／MDX 或执行能力。

### GitLab Wiki：资料仓库可以独立于业务代码

GitLab Wiki 为每份 Wiki 使用单独的 Git 仓库，可通过网页或 Git 编辑，资料与业务源码分开。[Wiki](https://docs.gitlab.com/user/project/wiki/)

这支持 CoSeed 内部托管独立资料仓库的方向，但不直接证明结构化图数据应该采用哪种格式，也没有为 CoSeed 定义完整的解析和数据库索引协议。

## 4. 四种格式比较

| 方案                            | 优点                                                         | 代价                                                  | 对 CoSeed 的判断                             |
| ------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------- | -------------------------------------------- |
| 全 JSON，正文放字符串           | 原生解析，只有一种结构格式，易做字段校验，单对象单文件       | 多行正文成为带转义的长字符串，原始 Git 行级 diff 较粗 | 可行备选；结构对象适合                       |
| 全 YAML，正文用多行标量         | 结构和正文可在单文件表达，行级差异较易读                     | 增加解析依赖与标量／缩进等约定；需要固定读写配置      | 有先例，当前无必要全面采用                   |
| Markdown＋YAML frontmatter      | 单文件保存元数据和正文，人工阅读与编辑自然                   | 额外解析器、前置信息边界和文本规范；仍需 Schema       | 成熟备选，适合明确以人直接编辑文件为主的场景 |
| JSON 元数据＋独立 Markdown 正文 | 结构类型明确，正文原样保留，行级差异清楚，可复用现有基础能力 | 一对象多文件；必须检查配对，统一保存和删除            | 当前推荐，作为待确认的协议方向               |

MCP 直连意味着 Agent 不必接触物理文件，因此“人必须舒服地手写 YAML”不是本项目首要前提。推荐保留 Markdown，主要是为了资料可导出、历史核对直观和正文保真；不是要求用户管理另一份本地仓库。

## 5. 本地实验

复现脚本：[research-content-formats.mjs](../../scripts/research-content-formats.mjs)。原始结果：[git-content-format-experiment.json](git-content-format-experiment.json)。

脚本只在系统临时目录下载固定研究依赖 `yaml@2.9.1`、`gray-matter@4.0.3`，使用结束后删除，不修改项目依赖和 lockfile。运行需要 npm 网络访问：

```bash
node scripts/research-content-formats.mjs
```

用一份合成的 12 段中文 Markdown 文本，包含标题、表格、TS 代码块和正文分隔线，仅修改第 6 段一句话。以下是 Git `--no-index --unified=0` 输出中增删内容行的 UTF-8 字节数，排除文件头与 hunk 头：

| 格式                 | 单对象文件数 | 样本总字节 | 增删内容行数 | 增删内容行字节 |
| -------------------- | ------------ | ---------- | ------------ | -------------- |
| JSON                 | 1            | 2135       | 2            | 3976           |
| YAML                 | 1            | 2104       | 2            | 302            |
| Markdown frontmatter | 1            | 2058       | 2            | 298            |
| JSON＋Markdown       | 2            | 2091       | 2            | 298            |

这些数字说明的是**该样本原始文本 diff 的阅读粒度**，不是 Git 网络流量、pack 压缩效果、存储膨胀、模型 token 数或系统吞吐测试。文件大小差异很小，不能据此宣称格式带来显著容量优势。应用层把 JSON 字符串解析后做段落 diff，也能改善全 JSON 的历史阅读。

另做 6 类精确值往返实验：普通富文本、含特殊字符的元数据、无结尾换行、正文前置空行、CRLF 正文和空正文。

- JSON、YAML、JSON＋Markdown 在该配置下各 6 类保持原值。
- `gray-matter.stringify` 的本次配置在“无结尾换行”和“空正文”两类改变了正文末尾换行，其余 4 类保持原值。它不代表 Markdown 格式本身不可保真；采用该路线需要定义规范化策略和对应测试。
- 实验配置拒绝重复 YAML 键，并显式排除 JS／CoffeeScript frontmatter 引擎。TinaCMS 源码也显式禁用了这些执行型引擎。[源码](https://github.com/tinacms/tinacms/blob/main/packages/%40tinacms/graphql/src/database/util.ts)

来源原文不应因正文规范化而悄悄变化；若保存源码、对话或日志材料，其字节／文本保留约定需单独明确。

此实验没有覆盖大型项目索引速度、Git 历史增长、并发保存、格式迁移和全量恢复，不能作为容量或可靠性验收。

## 6. 建议的 CoSeed 文件分工

以下是结构示意，**不是已定稿的正式协议**。文件路径以对象稳定 ID 组织，不以标题决定身份。

| 资料               | 建议载体                                                             |
| ------------------ | -------------------------------------------------------------------- |
| 格式版本及项目归属 | 仓库入口 manifest JSON                                               |
| 节点、连线、图清单 | 按稳定 ID 的 JSON 文件                                               |
| 需求、推进记录     | 每对象一份 JSON 元数据和一份 Markdown 正文                           |
| 项目综述           | JSON 保存概念、关系、示例清单；固定正文槽位对应 Markdown 文件        |
| 技术说明           | JSON 保存标题和成员，Markdown 保存问题说明                           |
| 原始依据           | 类型、定位和原文按严格来源模型保存；不将其自动变成待格式化正文       |
| 保存操作           | 系统时间、实际入口、执行信息和引用映射，由服务管理；具体文件表达另定 |

例如：一条需求可以对应 `requirements/<id>/metadata.json` 与同目录 `body.md`。前者保存标题、状态等字段，后者保存正文。MCP 可继续提交一个包含 title、status、markdown 的逻辑对象；服务负责拆分和还原，文件元数据不再重复保存正文。

不要根据“超过多少字符”动态决定是否生成 Markdown 文件。一个字段的物理映射应固定，否则同一业务对象会因措辞长度改变而切换格式。两文件中 ID／路径的对应、正文是否允许为空、换行约定和孤立文件处理都要进入正式协议。

读取必须固定同一个 Git 提交：不能在读完 metadata 后换到新 HEAD 再读正文。写入必须先对整份候选内容校验，然后一起形成一次 Git 提交，不能按文件逐个发布。

## 7. 解析与索引的建议边界

1. 以项目和固定提交取得 manifest，并按格式版本选择解析器；未知版本明确报错。
2. 根据规范中的种类和固定路径读取 JSON、正文；检查缺失、重复身份、项目归属和文件配对。
3. 还原统一逻辑对象，再用内容 Schema 和跨对象规则检查关系、图范围及具体来源。Schema 合法不等于需求真的完整、依据真的足够。
4. 生成绑定该提交和解析器版本的查询索引；页面只读取明确已发布版本，不能混合多个提交的结果。
5. 保留可从固定提交全量重建的入口。初期可以先做完整校验／重建，再以实测决定增量优化；格式或解析器变化时要有重建策略。

索引应能区分已保存 Git 提交、已索引提交和已发布提交。Git 和数据库不构成一个共同事务，解析／索引失败必须可识别和恢复，不能仅凭 Git 保存成功宣称全部完成。

业务历史定位使用“稳定对象 ID＋Git 提交”，不额外复制一套不断累加的对象版本目录。Git 时间不能代替推进记录的实际发生时间；一次 Git 提交也不能代替一条真实业务结论。具体到状态变化所依据的记录版本和更正来源，仍需在统一协议中表达。

## 8. 下一步与未决项

优先确认上述文件分工，再设计正式格式版本、对象 envelope、正文槽位、引用类型和来源表达，编写可执行 Schema、codec 及固定快照验证。MCP 输入输出沿用相同逻辑内容 Schema，物理存储 codec 放在服务侧。

现有 SQL 草案不能直接作为新索引表迁移。数据库项目元数据仍是独立持久化内容，只有 Git 内容对应的查询索引可从 Git 重建；备份不能只覆盖其中一个存储。

当前未做最终选择的部分：不同业务分支的资料发布入口、大量正文文件的性能、外部附件、远程身份授权和完整批量提交契约。本调研不据此增加未约定的用户体系、插件协议或客户端安装要求。
