# CoSeed 图形方案调研（2026）

核对日期：2026-11-05。结论是针对 CoSeed 的选型建议，不是全行业排名。已核对官方文档和 npm 元数据，X6、React 适配包和 ELK 已安装并锁定依赖；业务设计页已接入完整虚构模块图，未做其他主引擎的同场对比。

## 要解决的问题

CoSeed 的图不是统计图表，主要承载概念关系、用例、模块职责和内部设计。现有业务图需要：

- 自定义节点：名称、凝练业务描述、TS 类型和行内注释。
- 嵌套区域：模块边界、目录区域、边界外对象，目录完整路径从 `modules/` 开始。
- 关系表达：不同箭头和线型、业务说明、语义函数式请求/返回、多重性 `1`、`0..*`。
- 通用布局：尺寸和标签参与计算，跨边界连接，不能按示例项目手写坐标。
- 阅读交互：综述页固定适应画布；业务设计页按其阅读需求配置交互。保留低饱和纸面手绘视觉，不自动恢复已经移除的 Hover、展开或编辑行为。

## 候选比较

| 方案          | 已核对的基础能力                                                       | 对 CoSeed 的判断                                                                          |
| ------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| AntV X6 3     | SVG/HTML 图元、React 节点、分组、连接端点、多标签、正交及避障路由      | 首选候选。更贴近带边界、端点和关系标注的架构图；复杂排版仍需 ELK 和适配代码               |
| React Flow 12 | 自定义 React 节点和边、分组与跨分组连接；官方列出 ELK/Dagre 等布局集成 | 主要备选。React 组件组合直接；长边标签、多重性及 ELK 路径仍须专门适配，不能用默认连线代替 |
| AntV G6 5     | 关系图可视化、Combo 嵌套分组                                           | 更适合关系网络和图分析。当前产品更强调结构化卡片、明确边界和工程关系，因此不作主引擎      |
| Mermaid       | 用文本生成流程、状态、时序、实体关系等图                               | 适合后续文档里的标准小图。不能直接替代我们已经约定的富节点和交互表现；首版不额外安装      |

这些是应用适配判断，不表示其他方案不能实现。X6 和 React Flow 均不是现成的 CoSeed：业务含义、节点覆盖范围、来源和版本变化仍由产品模型负责。

## 推荐组合

**X6 3 + x6-react-shape 3 + ELK.js。**

- X6 负责图元、连接端点、关系线与标签的呈现和交互；卡片内部用 React。
- ELK 负责节点、嵌套分组、端点、边和标签的统一布局。Layered 支持正交路由及启用相应配置后的跨层级边。
- CoSeed 负责节点/关系语义、文字尺寸测量、坐标转换、可读性约束和布局结果检查。

X6 的 `manhattan` 是局部避障路由，不是全图自动布局，也不承诺避开所有标签。ELK 已输出路径时，应保留它的路由结果，不再让 X6 独立重算而破坏标签位置。跨层级边可能由多段组成，须正确转换坐标、锚点和边界。

React 节点使用 Portal 模式以访问应用 Context，确保 Ant Design 主题及应用状态一致。X6 3 与 React 适配包 3 配套使用；peer 范围覆盖 React 19，不等于已验证 StrictMode 下挂载、卸载和重渲染行为。

不以“底层必须是 Canvas”为目标。X6 主要使用 SVG/HTML，可以直接服务于现有卡片和文字阅读需求；Canvas 与否不决定图是否正确或布局是否紧凑。

## 锁定前的实测门槛

用现有完整业务图验证，不另造一个只有几个方框的演示：

1. 保留内部处理组件、业务对象、外部对象及现有关系，不为引擎删减业务。
2. 一套规则生成嵌套目录区域和边界外对象的位置；输入顺序打乱后布局仍可复现。
3. 测量中文说明、TS 字段、单行目录路径、关系标签和端点多重性，检查碰撞及越界。
4. 复用既有图模型验证和几何质量检查；实际检查线穿节点、标签遮挡、边界标题冲突及缩小后的可读性。
5. 验证 React 19 + Ant Design 主题、窗口尺寸变化、重复切换页面后的销毁与事件清理。
6. 综述图保持固定适应画布、禁止缩放和拖动；业务图按既定交互验收。

如果 X6 在真实图上的适配成本或质量不达标，再以相同输入和检查比较 React Flow。不能仅凭文档就宣称组合已经解决全部布局问题，也不同时引入两个主引擎。

## 性能验收

功能和性能共同决定是否锁定选型。下方保留测量方法，实际采样见文末；不将引擎宣传、节点数量演示或 HTTP 空路由跑分作为 CoSeed 的性能结论。用户已明确性能目标为够用且不耽误操作，不以极限帧率、容量或跑分为开发目标。

| 场景           | 测量内容                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------- |
| 首次进入图页面 | 资源加载、数据读取、文字测量、布局计算、节点和标签绘制、首次可操作分别耗时多少           |
| 拖动和缩放     | 在允许这些操作的图页测帧耗时和长任务；保持完整业务文字、字段、关系标签及边界             |
| 内容更新       | 局部文字或节点变化触发多少重渲染、是否重复布局，旧布局结果是否覆盖新内容                 |
| 连续使用       | 多次切换图页后，检查内存趋势、残留 Worker 和事件监听，不把等待 GC 的瞬时增长直接判为泄漏 |
| 页面体积       | 首屏压缩资源体积、图形引擎加载成本；评估将图形模块按路由懒加载                           |

先使用现有完整业务图，再构造约 100 节点 / 200 边及 300 节点 / 600 边的压力数据，保留代表性的长标签、字段和嵌套区域。这些是测试规模，不是已经承诺的容量。大图应同时评价可读性，不能仅靠缩成不可读文字获得性能结果。

在同一机器、浏览器、窗口尺寸和生产构建下比较，区分冷启动与缓存命中，多次运行并记录 P50/P95；交互性能使用有界面的浏览器测量。首轮基线建立后，再设定可复现的数值预算。

ELK 优先在 Web Worker 中运行，避免布局计算占用 UI 主线程；这不会自动加速文字测量或 React/SVG 绘制，仍需分别测量。按内容和布局配置识别是否需要重排，不在 Hover 或画布平移时重算布局。优化遵循测量结果，不能通过隐藏已约定的核心信息或削弱布局检查换取分数。

## 2026-11-10 实施采样

正式页面已接入 X6 + ELK，版本和交互见 [阅读规范](../requirements/business-reading.md)。polygon-clipping 0.15.7 用于交叉技术范围的布尔几何，不承担节点或边布局。

在当前开发机 Node 26.13.0、ELK 0.12.1 进行一次合成数据采样，保留说明、代表性 TS 字段尺寸、280px 关系标签和多目录分组。可复现命令：`node --import tsx scripts/measure-business-layout.mjs`。

| 节点／边  | 两方向布局与几何检查总耗时 | 选中结果尺寸  | 几何检查 |
| --------- | -------------------------- | ------------- | -------- |
| 100 / 200 | 620ms                      | 8888 × 18523  | 通过     |
| 300 / 600 | 2592ms                     | 21752 × 61902 | 通过     |

这是 Node 内的算法单次采样，不含 HTTP、DOM 测量、React 绘制或交互，不是浏览器 P50/P95 或容量承诺。结果面积很大，也说明「能算出来」不代表「整张图适应后还能读清所有文字」。当前生产浏览器验证覆盖 13 个完整节点、13 条关系、三项说明（两项交叉）、多目录及五个边界外对象；大图的浏览器耗时、长任务、帧率及长期内存仍待测量。

## 浏览器可用性检查与收口

同机 Chromium 生产构建、有界面模式、1440×1000、串行测试；完整 13 节点样本覆盖全部关系及交叉说明，100／200、300／600 为带字段、说明和多目录的合成读取关系样本。数据经真实 MCP 写入临时数据库，没有修改个人项目。首次进入使用全新浏览器上下文，重复进入沿用页面进程；「完整帧」等待所有卡片和关系文字挂载后再等两次动画帧，含自动化等待开销，不代表网络冷机。

优化前各采样 5 次：首次进入中位数约 1.34／1.99／4.75 秒，重复进入约 0.30／1.35／3.42 秒（按 13／100／300 节点）。300 节点样本的主要耗时是重新计算布局，因此仅增加有界 LRU 几何缓存，并在测完后销毁隐藏测量卡片。没有启用节点裁剪、隐藏字段或改用其他图引擎。

优化后仅对 300／600 做够用性复测：单次首次约 5.09 秒，重复进入约 0.80 秒；冷启动没有宣称改善。支持拖动与缩放，退出图页后 Worker 数量归零。该次结果不是 P95、长期内存稳定性证明或容量承诺；第一轮统计也只有 5 次，P95 实际等于样本最大值。

手工诊断入口：`COSEED_PERF_SAMPLES=1 npx playwright test --config playwright.performance.config.ts --grep '300 nodes'`。使用已有 Playwright 与真实临时服务，结果写入 `test-results/performance/**/metrics.json`；可额外设置采样次数，但不新增日常 CI 跑分门槛。原始诊断输出留在忽略目录，不收录项目资料或浏览器堆快照。

按用户要求到此收口：首次打开、重复切换和基本交互能否顺畅使用优先；后续只有真实卡顿影响工作时才继续测量与优化。
