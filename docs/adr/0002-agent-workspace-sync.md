# ADR 0002：Agent 直接接入 MCP，服务端用 Git 管理项目资料

状态：**方向已确认，尚未实现业务链路。** Agent 产品使用自身的 MCP 客户端能力直接连接 CoSeed 服务；CoSeed 内部复用原生 Git 保存项目资料及历史，数据库为这些内容提供查询索引。第一版不要求安装本地连接器，不要求业务仓库保存 CoSeed 文件。本文件替代先前的独立本地工作副本／连接器建议。

当前代码仍是 ADR 0001 描述的本机服务，仅支持 MCP 握手和 ping；已确认的目标架构与已运行实现分别记录，不把本次文档更新当成远程部署和业务工具完成。

## 1. 职责和存储位置

| 部分                     | 职责                                                                             |
| ------------------------ | -------------------------------------------------------------------------------- |
| Agent 产品               | 通过现有 MCP 客户端读取／提交项目资料，在自己的执行环境阅读并修改业务代码        |
| CoSeed MCP 入口          | 项目选择、资料读取、修改提交、历史查询；与 Web 复用业务校验和保存能力            |
| CoSeed 业务服务          | 项目权限、内容 Schema、来源和引用检查、旧版本冲突检查、保存和发布结果            |
| CoSeed 内部 Git 数据仓库 | 每个项目的综述、需求、推进记录、图和技术说明、来源及修改历史；这些内容的权威存储 |
| 数据库                   | 项目及必要服务元数据；Git 内容的查询索引和索引进度。被 Git 管理的内容索引可重建  |
| Web                      | 阅读服务端已发布版本；提供编辑时也走同一内容保存路径                             |
| 业务 Git 仓库            | 业务代码及其版本，仍由用户和 Agent 管理                                          |

MCP 是对 Agent 的业务接口，不要求 Agent 直接 clone、push 或操作 CoSeed 的服务器文件。Git 是服务端存储和版本底座；不需要为了这个入口先建设对外 Git 托管平台，也不自行实现 Git 对象、差量和合并算法。

MCP 接口仍需自己的内容读取、批量提交和错误契约；复用 Git 不会自动提供业务结构校验、项目权限或分页。具体工具名、参数和文件格式尚未定稿。

## 2. 从首次使用到页面展示

以下“订单系统”、P1、C42、D8、D9 均为示意，不是现有生产数据。

### 第一步：创建项目

用户在 CoSeed 页面建立“订单系统”，获得稳定项目 ID P1。服务在内部创建该项目的数据 Git 仓库及最小合法初始结构。无内容时如实为空，不生成虚构的需求或图。

创建项目不要求填写业务仓库地址。业务仓库地址可以作为可选定位材料，不因此授予 CoSeed 业务源码访问权。服务无须知道用户电脑上的业务目录。

### 第二步：Agent 连接 MCP 并选择项目

用户使用 Agent 产品已有的 MCP 配置能力，填入 CoSeed 服务地址及必要连接凭据。项目 P1 由用户明确指定或通过项目查询选择，不能从目录名猜测。配置不包含独立本地连接器。

对 MCP 协议能力的依赖与对特定客户端版本的实际验证不同；具体产品连接仍须集成验收，当前不提供未经验证的配置命令。

### 第三步：读取完整现状

Agent 通过 MCP 读取 P1 的综述、所有需求、全部推进记录，以及全部图、节点、关系和技术说明。服务返回固定的数据提交，例如 D8，以及完整性清单。

内容较多时分批读取，每批固定 D8，不能一部分取 D8、一部分取后来的 D9。历史修订与原始依据可通过历史／来源入口读取，不能把只返回目录宣称为正文已完整读取。标准 MCP 列表分页不等于自定义工具结果自动分页，业务内容的分页和完成条件仍需正式契约。

数据经 MCP 到达 Agent；不要求先有本地资料仓库。Agent 若需要保存到本地，使用其实际具备的文件能力形成临时副本，属于客户端行为，不是产品前提。完整资料可访问也不表示全部正文自动常驻模型上下文。

### 第四步：首次整理或继续开发

新项目：用户让 Agent 结合本地业务代码、已有文档和实际讨论梳理，Agent 在自己的执行环境阅读材料，形成综述、当前需求和设计图。

已有项目：Agent 先阅读已有内容，再围绕用户任务核对代码、实现和验证。第一次整理不能凭 Git log 虚构需求讨论；代码不能代替用户意图的原始来源。

需求推进主要由明确发起的回顾补齐，不把每次代码编辑自动当成一条进展。图的同步同样是明确的内容更新动作，而非服务器直接观察用户磁盘。

### 第五步：通过 MCP 提交相关修改

Agent 通过 MCP 提交本次新增／修订的对象、具体来源及所依据的数据版本 D8。未修改内容无需原样上传；共享节点的变动必须核对所有受影响的当前图。

代码对应关系独立于 CoSeed 数据版本。假设业务代码为 C42，本次资料注明依据 C42 核对；尚未提交代码时，保留实际 Git 基准及相关文件内容标识，不能只用 dirty=true 代替具体状态。CoSeed 不自动替用户提交业务代码，也不能直接证明远端工作区的最新情况。

### 第六步：服务校验、Git 保存、数据库索引、页面发布

服务校验项目权限、结构、引用、原始依据和基准版本。若当前数据已不是 D8，返回冲突事实，保留既有内容；不由服务自动改写业务含义。第一版推荐按项目基准进行冲突检测，细粒度并发合并留待实际需要。

校验通过后，服务把关联修改形成一次 Git 提交 D9，保留实际保存时间、执行信息和提交来源。Git 提交是一组内容变化，不替代每条需求／推进记录的稳定 ID、实际发生时间和业务语义。

相同逻辑提交的超时重试不得重复产生提交或推进记录，须在正式协议中明确操作身份及幂等规则。现有 1 MiB 请求限制下，大批修改的暂存／整批发布方式仍待设计，不能分块直接发布半张图。

Git 接收和数据库索引不是同一个事务。按提交更新索引，索引成功后页面发布 D9；索引失败时保留可读的上一版本、明确未完成结果，并可根据 Git 提交重建索引。读取响应必须说明所读提交，不能把落后的索引标成最新。

## 3. 日常一轮例子

1. Agent 经 MCP 读取 P1 的 D8 现状。
2. 用户要求增加订单取消功能，Agent 在本地业务仓库实现并验证。
3. 用户发起回顾／同步；Agent 整理需求变化、新结论和图的变化，附具体依据。
4. Agent 经 MCP 提交这批变化及基准 D8；假设核对的业务代码版本为 C42。
5. CoSeed 校验并形成数据提交 D9，索引完成后页面展示 D9，标明与 C42 的对应关系。
6. 下一次任务从 MCP 读取最新资料继续，不要求用户手工维护另一份本地 Git 仓库。

如果网页或另一个 Agent 已写入新版本，原 Agent 的旧基准提交应被拒绝；Agent 重新读取变化、核对后再提交。网页编辑必须经过同一 Git 保存和索引路径，不能只改数据库。

## 4. 对既有数据设计的影响

原有 8 表及业务设计 16 表 SQL 草案基于数据库权威内容和对象版本模型，不能原封不动作为本方向的正式迁移。应重审服务元数据、Git 内容文件、提交对应索引及发布状态之间的边界。

内容的业务语义继续成立：稳定 ID、记录新增与修订区别、真实状态变化、具体来源、图引用合法、保存时间与实际发生时间分开。Git 历史不自动证明这些语义，也不能把一个 commit 当成一条业务推进记录。

图文件、共享对象和历史引用的正式格式需按 Git 快照收敛，不能同时把数据库旧版本号和 Git 提交维护成两套独立权威历史。

## 5. 实现前仍需收口

- Git 数据文件格式、提交元数据、依据和单条记录修订的表达；数据库索引重设计。
- 固定提交读取、全量完成清单、批量提交、冲突和超时重试的 MCP 契约。
- 远程身份认证、项目授权及部署边界；现有实现仍限制为本机，不能直接放开监听。
- 不同业务分支的数据发布入口和项目默认视图，避免分支结果交替覆盖同一“当前设计”。
- Git 保存与索引发布的恢复机制、实际容量和性能验收。

本次只更新已确认方向和操作流程，没有新增接口、安装本地组件、创建数据 Git 仓库或修改运行时数据库。基础 Git／MCP 能力与业务端到端验收分别验证。
