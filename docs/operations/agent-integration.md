# Agent 接入与使用指南

本文说明开发者和 Agent 如何使用 CoSeed 读取项目资料、回顾工作、维护内容并确认保存结果。章节按实际工作顺序排列，接入流程与内容编写要求采用同一份正文。

页面展示本文；`read_guide(topic="usage")` 返回全文。其他主题提取对应章节，并按主题附带当前内容 Schema。

## 1. 明确任务

### 任务目标

Agent 的任务是结合用户目标、项目资料和实际实现，维护项目综述、需求推进记录及业务设计，并保留各项结论的来源和历史。开发者应能据此了解产品需求、需求演变及模块实现，并在工作中断后恢复必要的项目上下文。

本项任务使用以下材料：

| 材料                     | 可支持的判断                       |
| ------------------------ | ---------------------------------- |
| 用户提供的目标和实际讨论 | 需求意图、范围、已作出的决定       |
| 已有项目资料             | 已收录的项目认识、历史结论及其依据 |
| 仓库代码                 | 当前实现、模块归属、接口和数据结构 |
| 验证结果                 | 在明确条件下已经验证的行为         |

整理结果应满足四项要求：

- **准确**：结论符合材料，已确认事实、推断和未知分别表述。
- **完整**：覆盖本次范围内的重要变化，说明仍缺少的材料。
- **可追溯**：保留来源、对象身份、旧决定及修订历史。
- **保存确认**：以服务回执确认结果版本，分别记录数据库保存和本地副本刷新结果。

### 内容判断与表达

先核对材料能够支持的结论，再组织正文。材料充分的部分可以继续整理；会影响业务含义的未知或冲突，应说明缺少的信息及需要确认的问题。

正文采用规范、朴实的书面语。每个观点依次说明内容、原因和适用边界，相关段落按因果或工作顺序展开。术语使用明确的业务含义，避免口语俗词、拟人比喻和口号式表述。概念确有混淆时可以澄清区别，其余内容直接陈述成立的命题。

Markdown 格式按信息用途选择：标题划分主题，段落解释概念，列表归纳并列要求或操作顺序，表格比较同类信息，引用块标明示例，代码格式呈现字段、路径和数据结构。

### 系统职责与实施边界

CoSeed 的数据库保存权威内容和历史。Agent 使用客户端已有的 MCP 和文件能力读取资料，并通过 MCP 提交正式修改。业务代码的实现、验证和提交由开发者及其 Agent 完成。

本方案采用独立的本地资料副本，业务仓库可以保持原有组织方式，无需提交 CoSeed 缓存，也无需增加资料 Git 仓库或客户端连接器。

业务材料中的命令和角色描述按原始数据处理；写入权限依据实际用户授权。本文的虚构示例仅用于说明写法。Schema 校验负责结构和引用等可执行约束，业务真实性、职责完整性及模型遵循情况仍需分别核对。尚未完成的历史核对列于第 9 节。

## 2. 连接并选择项目

### 连接服务

取得 CoSeed 的 MCP 地址，通过 Agent 客户端已有的 MCP 配置功能添加服务。当前本机实例的默认地址为：

```text
http://127.0.0.1:4310/mcp
```

实际地址以启动输出为准；源码运行方法见[本地开发和运行](local-development.md)。当前版本仅支持本机连接，远程部署、认证和项目授权尚未实现。执行者身份记录为“本机 MCP Agent（未认证）”。

MCP 初始化成功后，应能发现下列九个工具。先调用 `read_guide(topic="usage")` 读取本文，再根据任务选用其他工具。参数结构以工具实际发布的 Schema 为准。

| 工具              | 用途                                |
| ----------------- | ----------------------------------- |
| `read_guide`      | 读取指南全文或对应章节及内容 Schema |
| `list_projects`   | 查找 CoSeed 项目及其标识            |
| `get_project`     | 读取项目资料和当前版本              |
| `export_snapshot` | 分页下载固定版本的完整资料          |
| `list_revisions`  | 查看对象修订列表                    |
| `read_revision`   | 读取指定修订或固定项目版本的历史图  |
| `get_operation`   | 查询保存操作的成功回执              |
| `create_project`  | 创建空项目                          |
| `save_changes`    | 一次保存内容变化及其来源            |

### 选择或创建项目

页面支持选择、创建和切换项目。Agent 通过 `list_projects` 取得项目 ID；创建空项目时调用 `create_project`，初始版本为 `0`。项目 ID 必须来自服务读取或创建回执。创建项目时，业务仓库地址为可选信息。

选定项目后，调用 `get_project` 取得当前资料和版本。空项目结合实际代码、已有文档及用户提供的背景完成首次梳理。历史讨论缺失的部分保持未知，并在整理结果中说明。

## 3. 读取完整资料

### 确定读取版本

开始新任务或恢复会话时，先检查项目版本。已有本地副本落后于当前版本时，重新下载完整资料。

`export_snapshot` 的所有请求固定使用同一组 `projectId` 和 `version`。完整副本用于搜索和核对项目资料；加入模型上下文的内容根据当前任务选择。

### 读取清单和文件

下载按以下顺序进行：

1. 使用 `part.kind="manifest"` 分页读取文件清单；后续请求将上次返回的 `nextAfterPath` 填入 `part.afterPath`，直到返回 `null`。
2. 核对各页的 `serviceId`、`version` 和 `manifestSha256` 一致。
3. 使用 `part.kind="file"` 读取清单内的文件，按返回的 `nextOffset` 继续获取字节。
4. 解码并拼接全部字节，核对每个文件的大小和 SHA-256，以及整个清单的摘要。

文件读取参数和结果如下：

| 字段         | 含义                                    |
| ------------ | --------------------------------------- |
| `path`       | 服务清单中的文件路径                    |
| `offset`     | 当前读取位置，以字节计                  |
| `maxBytes`   | 本次请求的最大字节数，上限 `65536`      |
| `content`    | Base64 编码的文件片段，解码后再写入文件 |
| `nextOffset` | 后续读取位置                            |

`nextOffset=null` 表示该文件读取完成。文件内容采用 UTF-8 编码的规范 JSON，并以换行结束。文件路径由服务生成，读取范围限于清单内路径。

清单摘要采用 **RFC 8785 规范化与 SHA-256**，计算对象包含以下字段：

```text
{ formatVersion, serviceId, projectId, version, files }
```

其中，`files` 按路径升序排列，每项只含 `path`、`bytes` 和 `sha256`；清单自身不计入 `files`。`formatVersion=1` 标识文件协议版本，`version` 标识项目内容版本。

### 理解资料范围

当前资料包含项目、综述、全部当前需求、推进记录、回顾、设计实体、关系、图和技术说明，以及它们实际引用的来源。

每个对象文件保存完整修订元数据、正文、来源引用和链接。`history` 补充当前资料所引用的固定旧修订和历史图；额外历史可通过修订工具查询。历史图的全部成员按同一 `projectVersion` 解析。已移除对象保留在需要它的固定历史引用中，当前集合只包含当前有效对象。

### 保存本地副本

Agent 使用客户端自身的文件能力写入资料。建议目录为：

```text
<cacheRoot>/<serviceId>/<projectId>/versions/<version>/
```

先下载到独立的 `staging` 目录，完成全部文件及清单核对后，再切换读取指针。下载中断时保留上一份完整副本。缓存可以删除后重建，权威内容始终保存在数据库中。

`export_snapshot` 仅返回数据，本地文件由客户端写入。缺少文件能力的客户端可以直接读取工具结果，并应准确说明资料尚未写入本地文件。不同 Agent 客户端对 MCP 结果处理和文件写入的支持，需要分别验证。

当前实现使用不可变版本数据保证分批读取一致性，跨页读取无需长期数据库事务；进程重启后可重建相同字节。导出内存缓存上限为 `4` 项、`32 MiB`，有效期为 `15` 分钟。单次构建仍需读取完整项目及必要历史，超大项目容量尚未验证。

## 4. 推进并发起回顾

### 完成工作并保留实际结果

结合用户目标、现有资料和实际代码，确定本轮问题及影响范围，完成实现和必要验证。发现资料与代码存在差异时，记录差异及可核对的位置，供阶段回顾使用。

### 确定回顾范围

由用户明确发起阶段回顾或资料同步，并指定讨论和代码范围。一次回顾可以涉及多个需求，同一需求也可以在多次回顾中持续推进。

记录以有意义的结论或结果为单位，形成时机以用户指定的回顾为准。聊天轮次、工具调用和日期仅提供过程信息。

### 判断需要维护的内容

| 已确认的变化                   | 维护方式                                   |
| ------------------------------ | ------------------------------------------ |
| 对整个产品的认识发生变化       | 更新项目综述                               |
| 独立工作目标的内容发生变化     | 维护对应需求                               |
| 形成新决定、方案变化或实际结果 | 新增推进记录                               |
| 既有记录与原始事实不符         | 修订原对象并保留历史                       |
| 模块实现或职责发生变化         | 更新受影响的节点、连线、数据结构和技术说明 |

一次回顾可以同时采用多种维护方式。保留未受影响的内容，说明材料不足的部分。

确定需要维护的内容后，调用对应的 `read_guide` 主题取得内容 Schema：`overview` 对应综述，`requirements` 对应需求、推进记录及回顾，`design` 对应图及其成员，`sources` 对应来源和引用。依据本文整理业务内容，按照 Schema 组织字段，完成来源关联后统一提交保存。

下文采用同一个**虚构预约项目**说明写法。示例中的业务范围、字段和数量只在该示例条件下成立。

## 5. 更新项目综述

综述表达项目当前的整体需求和业务认识，按产品表述、核心概念、使用示例组织。需求推进记录保存这些认识的形成和变化过程。

### 产品表述

产品表述应让初次阅读的人了解产品是什么、解决什么问题，以及当前已确认的业务范围。采用自然段落和必要的小标题，连贯说明当前需求。整体认识发生变化时，同步修订这一部分。

产品表述为必填内容。具体句式尚待核对，当前使用自然 Markdown 正文。

> **示例：产品表述（虚构预约项目）**
>
> 一个供小型工作室管理服务预约的系统。顾客查看服务和可预约时段后提交预约，工作人员安排时间并查看已确认的预约。
>
> 本例范围包括查看空闲时段、提交预约和取消预约；在线支付不在本例范围内。

### 核心概念

核心概念解释理解产品所必需的业务含义。概念的选择依据业务语义；数据库表属于实现结构。词条、关系、示例及用例图均归属于综述。

概念之间采用以下三种关系：

| 关系     | 含义及端点顺序                                         | 存储值        |
| -------- | ------------------------------------------------------ | ------------- |
| 种属     | 子类 → 父类，子类属于父类的一种类型                    | `kind-of`     |
| 组成     | 整体 → 部分，整体包含部分                              | `composition` |
| 业务关联 | 按 `source` 到 `target` 的顺序，用具体名称说明业务联系 | `association` |

词条缩进只表示种属，组成和一般业务关联通过对应关系表达。当前页面仍按词条平铺，展示差异列于第 9 节。

> **示例：概念解释（虚构预约项目）**
>
> **可预约时段**：某项服务当前可以接受预约的时间范围，供顾客选择。
>
> **预约**：记录顾客选定的服务、时段及当前预约状态，供顾客和工作人员确认安排。

### 使用示例

整组示例先说明参与者、当前情况、共同前提和要解释的使用过程。某节独有的前提写在该节正文中。

每个小标题下按以下次序呈现：

1. 对应该节描述的用例图。
2. 该节例子正文，以自然段落展开完整的使用过程。

正文采用自由 Markdown，可以包含必要的小标题。使用过程依据实际内容组织，步骤编号为可选形式。图按小节分别提供，整组示例采用各节图解释各节正文。

用例图的角色位于系统边界外，用例位于边界内。参与连线表达角色参与某个用户目标，执行先后应在正文中说明。同一角色可以参与多个用例，同一用例可以用于多个示例小节。每节的图和正文应引用一致的角色及用例。

材料不足时，概念和示例可以明确留空；提供示例小节时，开篇背景必须完整。内容完整性需要结合真实业务审查。

### 保存字段

| 字段               | 内容                                  |
| ------------------ | ------------------------------------- |
| `product.markdown` | 产品表述正文                          |
| `concepts`         | 概念词条及关系                        |
| `examples`         | 开篇背景、角色、用例和各节正文        |
| 对象 `id`          | 固定为 `projectId`                    |
| `expectedRevision` | 已读取的综述修订号；初次保存为 `null` |

一次保存提交完整 `overview` 内容。综述内部的概念、角色和用例使用局部 ID，原样保留在综述内部；其他项目对象使用服务提供的正式 ID。

## 6. 整理需求推进

需求表示可独立推进的用户目标，推进记录保存该目标下的结论和结果。先判断目标边界，再核对历史事实，最后确定新增或修订方式。

### 划定需求边界

需求正文说明服务对象、问题、范围和完成标准，字数依据内容确定。一个需求可以反复讨论、影响多个模块并积累多条推进记录。

共享同一用户目标、主要范围和完成标准的内容，继续归入原需求。另一个目标能够独立推进和验收，且推进与否可以单独决定时，建立新需求。需求身份在更换聊天、日期或产品版本后继续保留。

当前管理范围采用已经确定的需求字段。优先级、负责人、估时、迭代、百分比进度及依赖审批等尚未确认的管理字段，待相应使用需求确定后再设计。

> **示例：完整需求（虚构预约项目）**
>
> **顾客自主取消尚未开始的预约**
>
> 顾客的计划改变后，需要自行取消预约，减少与工作人员反复沟通。系统允许顾客查看并取消本人尚未开始的预约。
>
> 完成标准为：顾客可以取消符合条件的本人预约，取消后能查看结果；系统拒绝取消其他顾客的预约及已开始的预约。

### 编写推进记录

每条推进记录**有且只有一个主需求**，说明一项有意义的结论或结果，并保留理解它所必需的原因、约束和影响。

正文使用自由 Markdown，通常约 **100～200 字**。这是阅读建议，具体长度依据内容确定，句式和小标题可以自由选择。无关结果分别记录；同一结果涉及多个独立需求时，各需求分别记录自身结论，可以引用同一来源。

> **示例：推进记录（虚构预约项目）**
>
> **确定取消预约的范围**
>
> 本次讨论确定，顾客可以自行取消本人尚未开始的预约。取消成功后，顾客和工作人员都能查看取消结果。这项结论确定了取消范围和完成标准，后续 UI 设计和实现据此推进；当前阶段为方案形成，实现和验收尚待完成。
>
> 记录归入“顾客自主取消尚未开始的预约”。本例假设材料中缺少可核实的讨论时间，因此 `occurredAt` 填 `null`，保存时间由系统记录。

### 区分新增与修订

| 情形                                 | 处理方式       | 历史要求                                                           |
| ------------------------------------ | -------------- | ------------------------------------------------------------------ |
| 后来形成新决定或取得新结果           | 新增推进记录   | 保留当时成立的旧结论；承接或改变旧决定时，引用其具体修订并说明变化 |
| 原记录存在误记、遗漏、时间或归类错误 | 修订原记录     | 保留对象身份、修改前后版本和更正依据                               |
| 需求正文需要更正或更新               | 保存需求新修订 | 按实际结论判断是否同时新增推进记录                                 |

> **示例：两种处理方式（虚构预约项目）**
>
> 原讨论确定“尚未开始的预约”，记录误写为“所有预约”，应修订原记录并保留历史。
>
> 后续讨论决定扩大范围，允许取消已开始的预约，应新增推进记录，引用原决定的具体修订并说明变化。

### 填写记录属性

| 字段或时间             | 处理要求                                                      |
| ---------------------- | ------------------------------------------------------------- |
| `occurredAt`           | 结论或事件实际发生时间，单位为 Unix 毫秒；无法核实时填 `null` |
| `createdAt`、`savedAt` | 由系统分别记录首次收录和各次修订的保存时间                    |
| 首次捕获顺序           | 旧记录修订后继续保留                                          |
| `links`                | 明确的对象关联；省略表示沿用，`[]` 表示清空                   |
| 历史图链接             | 固定 `projectVersion`，使图中全部成员按同一项目版本解析       |

发生时间依据事件材料填写，更正时同样需要可核实的依据。保存时间由系统独立生成，未知的发生时间继续保留为 `null`。时间线默认按首次收录顺序倒序显示，修订保留原位置及其历史内容。

### 确定需求状态

依据需求的实际阶段选择状态，并保留支撑材料：

| 状态     | 含义                                       | 存储值                     |
| -------- | ------------------------------------------ | -------------------------- |
| 设计中   | 必要的需求理解、UI／交互或技术方案仍在形成 | `designing`                |
| 方案已定 | 必要设计已足以支撑实现                     | `ready_for_implementation` |
| 待验收   | 已有完整实现，约定要求尚待核对             | `pending_acceptance`       |
| 已完成   | 已核对并满足完成标准                       | `completed`                |
| 暂缓     | 当前决定暂时停止推进                       | `on_hold`                  |
| 取消     | 当前决定取消该需求                         | `cancelled`                |

必要设计已经确定、完整实现尚未确认期间，需求状态可以保持“方案已定”，具体的设计调整和实现活动由推进记录说明。六种状态均可回退、恢复和跳转；初次状态依据事实选择。工具调用、Agent 的完成报告和回顾保存回执，只能证明其各自对应的活动，状态判断还需核对该状态的成立条件。

已有需求的状态发生真实变化时，填写 `statusChange`：

| 字段                    | 填写要求                                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `statusChange.kind`     | 实际推进使用 `progress`，状态纠错使用 `correction`                                                                 |
| `statusChange.reasonMd` | 说明状态变化原因                                                                                                   |
| `statusChange.records`  | 实际推进至少引用一条同一需求下的固定记录修订，包含 `id` 和 `revisionNo`；状态纠错以 `citations` 中的原始来源为依据 |

初次建立需求时，在 `content.status` 中填写有依据的初始状态，通过 `citations` 提供来源；`statusChange` 省略或填 `null`。系统据此生成 `initial` 历史。正文修订而状态值未变时，`statusChange` 同样省略或填 `null`。

状态变化时间取最近一次真实状态值改变的保存时间。正文修订而状态保持原值时，沿用原状态变化时间。后续记录更正保留旧状态变化所引用的固定依据。

## 7. 更新业务设计

业务设计采用两层图。第一层说明项目的业务模块、职责和依赖；第二层以一个模块为范围，说明内部处理组件、业务对象及其关系。整张图表达所选范围内的完整结构和协作关系。

### 确定观察范围

| 图层     | 展示对象                       | 主要含义                                   |
| -------- | ------------------------------ | ------------------------------------------ |
| 项目全景 | 同层级业务模块及必要的外部系统 | 模块职责、功能依赖和业务联系               |
| 模块内部 | 处理组件和数据对象             | 模块内部如何实现职责，以及接触哪些外部对象 |

模块内部图以选定业务模块为边界：本模块所属对象位于边界内，其他模块或外部系统所属对象位于边界外。`owner` 保留对象实际归属。

依赖箭头指向提供能力的一方，描述结构上的能力使用关系。具体执行顺序需要另有行为依据。目录区域表示代码归属，技术说明范围表示采用同一技术机制的成员。

### 划分节点

**一张图的所有节点必须正交完备**：同一层级的职责归属明确、没有重复划分，所选范围内的必要职责均有对应节点。

先确定整张图的节点，逐项审查职责重叠和遗漏，完成审查后再补连线。业务完整性依据需求和实际实现审阅；结构、引用和绘制检查分别验证相应技术条件。

| 节点类型                   | 含义                                         | 直接展示的内容                        |
| -------------------------- | -------------------------------------------- | ------------------------------------- |
| 业务模块 `module`          | 一组业务职责及其边界，分为 `core`／`support` | 名称和职责                            |
| 处理组件 `component`       | 承担具体处理职责的实现部分                   | 名称和凝练、详实的职责说明            |
| 数据对象 `data_object`     | 具有业务含义和核心字段结构的对象             | 名称、业务含义、TS 类型及字段行内注释 |
| 外部系统 `external_system` | 当前项目之外参与协作的系统                   | 名称及协作职责                        |

处理组件正文以职责及业务效果为中心。类、方法和 CRUD 清单属于进一步实现信息，当前节点内容以表中范围为准。处理组件说明通常约 **40～70 字**，具体长度依据职责确定。

节点和连线均采用静态呈现，阅读所需信息直接可见。当前不提供 Hover 详情、点击展开或第三层代码页面。

> **示例：处理组件（虚构预约项目）**
>
> **预约取消处理**：核对预约归属和开始时间；满足当前顾客取消本人尚未开始预约的条件时，更新预约状态并返回结果，供顾客和工作人员查看。

> **示例：数据对象（虚构预约项目）**
>
> **预约**：保存预约归属、选定服务、开始时间和当前状态。
>
> ```ts
> type Booking = {
>   id: string; // 预约标识
>   customerId: string; // 所属顾客
>   serviceId: string; // 选定的服务
>   startsAt: string; // 预约开始时间，ISO 8601
>   status: 'confirmed' | 'cancelled'; // 本例预约状态
> };
> ```

### 表达目录归属

每个节点只选择一个最核心的真实实现来源，并按该来源目录归组。目录标题包含 `modules/` 时从该段开始，否则使用真实仓库相对目录。路径在区域标题中单行显示，节点正文保留业务内容。

缺少实现来源时，对应来源字段填 `null`，目录信息保持缺失。

### 选择关系类型

关系类型依据两端对象及实际关系选择：

| 关系及存储值                     | 两端及方向                                                | 线型           |
| -------------------------------- | --------------------------------------------------------- | -------------- |
| 功能依赖 `functional_dependency` | 依赖方 → 提供方；模块／外部系统之间，至少一端为本项目模块 | 虚线、开放箭头 |
| 模块关联 `module_association`    | 模块／外部系统之间，至少一端为本项目模块；无方向          | 实线、无箭头   |
| 调用 `call`                      | 调用组件 → 被调用组件                                     | 虚线、开放箭头 |
| 读取 `read`                      | 处理组件 → 数据对象                                       | 虚线、开放箭头 |
| 写入 `write`                     | 处理组件 → 数据对象                                       | 虚线、开放箭头 |
| 对象关联 `object_association`    | 数据对象之间；无方向                                      | 实线、无箭头   |
| 事件 `event`                     | 发布组件 → 订阅组件                                       | 点线、开放箭头 |

### 编写连线内容

每条连线保留业务说明，使读者直接理解关系用途。根据关系类型补充语义操作、关联约束或事件信息：

| 关系               | 内容要求                         | 表达格式                                 |
| ------------------ | -------------------------------- | ---------------------------------------- |
| 功能依赖、模块关联 | 所使用的业务能力或明确的业务联系 | 凝练、具体的业务说明                     |
| 调用               | 接口作用、核心输入和返回含义     | `动作（核心输入）：返回含义`             |
| 读取               | 查询依据及读取内容               | `读取动作（查询依据）：读取内容`         |
| 写入               | 定位依据及写入变化               | `动作（定位依据；修改内容）`             |
| 对象关联           | 业务含义、已知关联字段及两端数量 | 业务说明、关联字段和端点数量             |
| 事件               | 语义名称、实际事件标识及核心载荷 | `事件（核心载荷）`，同时保留实际事件标识 |

调用的返回信息写在原调用线上。对象关联使用关系及数量表达。已知数量绑定真实端点，布局换向后继续对应原端点，并用业务文字解释数量含义。

未知数量填 `null`；明确没有返回时写“无返回”，返回信息未知时写“返回待确认”。事件关系只说明发布和订阅，异步可靠性需由实际机制另行确认。

> **示例：调用（虚构预约项目）**
>
> 取消入口 → 预约取消处理：核对本人预约的取消条件并取得结果。
>
> `取消预约（预约标识、顾客标识）：取消结果`

> **示例：读取与写入（虚构预约项目）**
>
> 预约取消处理 → 预约：读取预约归属、开始时间和当前状态，用于取消判断；条件满足后保存取消结果。
>
> 读取：`读取预约（预约标识）：所属顾客、开始时间、当前状态`
>
> 写入：`取消预约（预约标识；状态改为已取消）`

> **示例：对象关联（虚构预约项目）**
>
> 顾客 — 预约：一位顾客可有多条预约，每条预约属于一位顾客。
>
> 关联字段为 `Booking.customerId`；顾客端为 `1`，预约端为 `0..*`；采用实线、无箭头。数量以本例已确认的业务条件为依据。

### 说明技术机制

技术说明以实际策略名称为标题，例如状态机、事务边界或策略模式。正文说明采用的机制、解决的具体问题及原因，设计理由融入问题说明。技术主题依据实际设计选择；成员范围通过图示和 `entityIds` 表达。

说明通过 `entityIds` 精确指定成员：单个节点的说明关联该节点，多节点机制关联全部实际成员。不同说明范围允许交叉，各自范围只包含真实成员。节点继续保留唯一目录归属。

> **示例：状态机（虚构预约项目）**
>
> 使用明确的状态迁移表达预约取消：符合取消条件的已确认预约可以转为已取消，使状态变化符合已确定的业务条件。
>
> 说明关联实施这项机制的“预约取消处理”和“预约”节点。

### 保存设计内容

| 字段或对象               | 处理要求                                                                         |
| ------------------------ | -------------------------------------------------------------------------------- |
| 组件和数据对象的 `owner` | 以 `owner.kind` 标明模块或外部系统，`owner.id` 指向实际归属对象                  |
| `primarySourceId`        | 对应 `kind=code` 且 `locator.path` 为真实仓库相对路径的源码来源；缺失时填 `null` |
| `typeSourceId`           | 可以指向类型设计材料；缺失时填 `null`                                            |
| 图的成员引用             | 使用稳定实体、关系和说明 ID，成员正文由共同对象提供                              |
| `scope.kind="project"`   | 仅包含模块及外部系统                                                             |
| `scope.kind="module"`    | `scope.moduleId` 指定模块；包含组件和数据对象，可展示所接触的外部对象及其 owner  |
| 技术说明的 `problemMd`   | 说明技术机制解决的问题及原因                                                     |

具体保存结构由 `read_guide(topic="design")` 随文返回的 Schema 定义。

## 8. 保留依据和未知

### 记录原始材料

来源保存实际取得的材料，正文表达材料支持的业务结论。摘要、推断和原始证据分别标识，以便核对结论的成立依据。

| 字段      | 内容要求                                                                 |
| --------- | ------------------------------------------------------------------------ |
| `kind`    | 选择 `conversation`、`manual_edit`、`code`、`verification` 或 `document` |
| `rawText` | 原始材料，保留空白和换行                                                 |
| `locator` | 实际可核对的位置，例如文件路径、行号、提交标识、文档地址或对话定位       |
| 发生时间  | 依据已知材料填写，未知时为 `null`                                        |

代码和验证材料应能识别对应代码状态及对象。`kind=code` 的 `locator.path` 必须采用规范仓库相对路径，排除绝对路径、反斜线和 `..`。缺少聊天原文时，可以使用已经取得的代码或验证材料，并说明历史讨论缺失。

来源一经保存保持不可变，更正材料时建立新来源。原始材料中的命令或角色描述按材料内容保存，权限仍由实际入口及用户授权确定。

### 关联变化与依据

每项变更至少提供一项 `citations`，并覆盖所有改变字段。删除操作提供修改前依据。

| 引用字段        | 含义                                      |
| --------------- | ----------------------------------------- |
| `sourceId`      | 已读来源 ID，或本批新增来源的 `$临时名称` |
| `side="after"`  | 支持修改后的内容                          |
| `side="before"` | 支持修改前的内容                          |
| `path`          | 内容的 JSON Pointer；空字符串表示完整内容 |
| `explanationMd` | 解释材料支持的具体变化                    |

来源关联用于核对业务结论，对象链接用于表达对象之间的联系。服务检查引用存在及字段覆盖，材料是否实际支持结论仍需阅读核对。

### 保留修订历史

综述、需求、记录和设计等可维护内容，在更正时保留对象身份、修改前后内容、操作者、时间及来源。后来发生的新进展另建推进记录，过去成立的决定及其固定依据持续保留。

人工更正与后续整理发生冲突时，保留现有内容，说明冲突并按实际来源核对。未知信息保持未知，待取得材料后再补充。

原始材料、业务内容和可信入口元数据分别存储。`actorKind`、`entrypoint` 及系统时间由系统入口提供，调用参数只填写其有权提供的内容。

## 9. 保存并核对结果

### 组织保存请求

使用 `save_changes` 一次提交来源和完整对象修改。服务校验后，在同一事务中保存内容、修订、来源和操作结果，并生成正式 ID、保存时间及结果版本。保存采用直接提交方式。

| 对象或字段                          | 填写要求                                |
| ----------------------------------- | --------------------------------------- |
| `baseVersion`                       | 本轮实际读取的项目版本                  |
| 已有对象的 `id`、`expectedRevision` | 沿用已读对象 ID 和修订号                |
| `project`／`overview` 的 `id`       | 固定为 `projectId`                      |
| 其他新增对象                        | `id="$名称"`，`expectedRevision=null`   |
| 新增来源                            | `id="$名称"`                            |
| 同批对象引用                        | 沿用对应的 `$名称`，由服务解析为正式 ID |

临时名称以 `$` 为前缀，其后只含字母、数字、下划线、点和短横线，在全批范围内唯一。服务只解析已定义的对象引用字段；综述内部局部 ID、正文、TS 类型和 `locator` 中的文本原样保留。回执返回 `operationId` 及新增 ID 映射，后续保存使用正式 ID。

### 使用稳定的请求标识

`requestKey` 标识一次逻辑保存，例如 `theme-review-2026-11-06`。创建项目时，该标识在服务实例内唯一；保存内容时，在项目内唯一。

| 情形                          | 请求标识及内容                                                 |
| ----------------------------- | -------------------------------------------------------------- |
| 已成功保存的请求重试          | 保持原 `requestKey` 和原始请求内容，服务返回原回执及其结果版本 |
| 新的逻辑保存                  | 使用新的 `requestKey`                                          |
| 已成功保存的 key 携带不同内容 | 服务返回 `OPERATION_MISMATCH`                                  |

超时后，通过 `get_operation` 按原 key 查询，或使用原 key 和原始内容重试。查不到成功回执时，保存结果仍待确认，应继续按同一逻辑保存处理。

### 处理错误和冲突

| 结果           | 处理要求                                                     |
| -------------- | ------------------------------------------------------------ |
| 基准或修订冲突 | 重新读取受影响资料，核对内容后重新形成修改                   |
| 内容校验失败   | 按实际错误修正内容，并保留尚未成功提交的修改                 |
| `NO_CHANGES`   | 内容、来源关联及移除状态均无变化，本次沿用已有版本           |
| HTTP `413`     | 请求超过 `1 MiB`，整批未保存；当前版本尚无分块上传和自动拆批 |

工具的业务结果包含 `summary` 和 `data`；业务失败包含 `error`，且 `isError=true`。HTTP 和协议错误按对应协议返回，结果结构可能不同。

服务检查结构、归属、版本、引用和来源覆盖。MCP annotations 描述工具能力；权限依据实际授权和服务端控制。

### 确认结果并刷新副本

保存与刷新按以下顺序核对：

1. 根据服务回执确认数据库已保存及其项目版本。
2. 下载完整最新快照，完成核对后切换本地读取副本。
3. 下载失败时保留旧副本及其真实版本，仅补做下载。
4. 向用户说明实际保存内容、验证结果、对应业务代码状态及未完成部分。

保存回执保持该次操作的结果。期间若有其他保存，最新项目版本可以高于本次回执。业务代码版本标识代码状态，CoSeed 数据版本标识资料保存状态，两者分别记录。

项目综述、需求推进和业务设计均已接入页面阅读。通过 `list_revisions` 和 `read_revision` 可以查看修订、来源及固定项目版本的历史图。

### 本版待核对

当前材料尚未覆盖完整历史，以下内容继续保留为待核对事项：

- **产品表述**：固定句式尚无完整依据，当前采用自然 Markdown。
- **核心概念**：选词粒度和解释长度尚待确认；种属缩进约定与当前平铺实现存在差异。
- **业务图完整性**：正交完备仍需按业务审查，现有结构和引用校验覆盖相应技术约束。
- **技术主题**：依据实际设计选择，分类枚举尚未确定。
- **回顾扩展**：失败草稿、自动运行及分批执行流程尚未确定。
- **历史依据**：更早文档记录的原始确认尚待逐项核对，文档记录与可见用户原话分别标识。
