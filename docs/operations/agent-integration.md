# Agent 写作规范

在 CoSeed 中，「概览」介绍产品及其用法，「结构设计」展示各个模块及其关系，「时间线」按目标组织进展记录。本文与 MCP 的 `read_guide(topic="usage")` 共用正文。工具描述和 Schema 定义参数及填写要求。

## 1. 明确任务

Agent 的任务是结合用户目标、项目资料、代码和验证结果，维护当前认识及其来源，使读者理解**结论、原因、边界和变化**。用户讨论支持意图与决定，代码支持当前实现，验证结果支持其条件内的行为；事实、推断和未知分别表述，影响业务判断的缺失或冲突需说明并确认。

**由用户明确发起阶段回顾或资料同步**，指定讨论及代码范围。一次回顾可涉及多个需求，一个需求可持续多次回顾。按重要结果维护内容：整体认识改变时更新综述，独立目标改变时维护需求，新决定或结果新增记录，原内容误记时修订，模块变化时更新受影响的设计。保留未受影响的内容，聊天轮次和工具调用只作为过程材料。

CoSeed 保存项目资料及历史，Agent 通过 MCP 阅读和提交变更。业务代码的实现、验证和提交在开发者的工作区完成。

### 内容表达规范

适用于本文及全部 Agent 正文；原始材料保留原文。

- **语体**：使用朴实、准确的书面语和明确术语；禁止口语俗词、拟人比喻和口号。
- **逻辑**：按理解顺序直接说明观点、原因和适用边界，段落按因果、条件或承接关系展开。禁止故意倒装逻辑；仅在确需澄清概念混淆时使用对举式、纠正式或反转式句型。
- **按内容选择 Markdown 格式。** 连贯的说明可以只用自然段。需要区分主题、比较信息、说明步骤、展示代码或标明出处时，再选用相应格式。

## 2. 连接并读取项目

在本机工作台选择项目，进入「接入指南」签发项目 Key。在客户端配置服务地址 `/mcp`，通过 Authorization 请求头以 Bearer 方式提供该 Key。连接仅能发现、读取和更新该项目。

从 MCP 资源列表打开项目的当前目录。目录给出本轮版本和正文地址。沿目录可读综述、需求及其记录、业务全景及模块内部图。按关键词查资料时用 `search_project`，一次读多项或客户端只提供工具时用 `read_resources`。`get_project` 也会返回同一版本的目录地址。恢复会话时重新打开当前目录。

**新项目的建档顺序。** 先保存产品说明正文，再一起提交工作方式导读与系统架构概览图。两者齐备后，可以一起建立核心概念、示例背景和业务全景中的模块。已有全景后，可以分别建立需求和模块内部节点。推进记录依赖已保存的需求，业务图上的连线和技术说明依赖该图中已保存的节点。

例如，核对一项需求时，先打开需求正文和最近的推进记录，再沿同版设计目录读取对应模块图。用户确认本次回顾范围后，将有材料支持的改动一次提交给 `save_changes`。保存回执给出新版本，下次读取当前目录即可看到变化。

## 3. 编写概览

概览说明**项目当前的整体需求**。页面从第 0 节的工作方式开始阅读。需求的形成过程和后续变化记入推进记录。

修改已有图时，按实际变化提交。一条概览连线可以单独修改，示例小节也可以单独增减选用的用例。

| 部分     | 编写要求                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------- |
| 如何工作 | 导读和概览图共同说明项目实际怎样运作。                                                                   |
| 产品说明 | 用自由 Markdown 说明产品是什么、为谁解决什么问题，以及已确认的业务范围。正文必填，段落按项目内容组织。   |
| 核心概念 | 选出读者理解业务所必需的概念，用项目材料核对名称和定义。每个概念写成词条，用关系说明概念之间的业务联系。 |
| 使用示例 | 开篇交代参与者、当前情况、共同前提和目的；每个小标题下先放对应用例图，再以自然段落讲清使用过程           |

概念关系：**种属** `kind-of` 为子类 → 父类，缩进仅表示种属；**组成** `composition` 为整体 → 部分；**关联** `association` 按 source → target 用具体名称说明联系。

用例图角色在系统外，用例在内，连线表示角色参与用户目标；先后由正文解释。每节图与正文引用一致，可复用角色和用例，整组仅保留各节图。独有前提写在该节，步骤编号按需使用。材料不足时概念、示例可留空，已有示例小节时必须提供开篇背景。

## 4. 说明结构设计

项目全景展示模块、外部系统及职责关系；模块内部展示一个模块的组件、数据对象和协作。图表达完整结构，执行顺序需另有行为依据。

### 节点和范围

**一张图的所有节点必须正交完备**：同层职责明确、无重复划分，必要职责均有节点。先审查职责重叠和遗漏，完成审查后再补连线；完整性需结合业务审阅。

| 节点                       | 直接展示内容                                   |
| -------------------------- | ---------------------------------------------- |
| 业务模块 `module`          | 名称、职责，分 `core`／`support`               |
| 处理组件 `component`       | 名称、处理职责及业务效果，说明通常约 40～70 字 |
| 数据对象 `data_object`     | 名称、业务含义、TS 类型及字段行内注释          |
| 外部系统 `external_system` | 名称、协作职责                                 |

节点静态显示必要内容，类、方法及 CRUD 清单属于更细实现；当前不提供 Hover 详情、点击展开或第三层代码页面。数据对象写法如下，字段按实际材料确定：

```ts
type Booking = {
  id: string; // 预约标识
  customerId: string; // 所属顾客
  startsAt: string; // 开始时间，ISO 8601
  status: 'confirmed' | 'cancelled'; // 本例预约状态
};
```

本模块对象在边界内，接触的其他模块或外部系统对象在外，并保留实际归属。

处理组件和数据对象各选一处最能代表其实现的代码来源。来源无法确认时记为未知。有明确来源的节点按实际目录归组。路径包含 `modules/` 时从该段开始，否则使用仓库相对目录。路径只在区域标题中单行显示。

### 连线

**每条线保留具体业务说明**，再补充下表信息：

| 类型                             | 两端、方向及线型                                | 补充内容                             |
| -------------------------------- | ----------------------------------------------- | ------------------------------------ |
| 功能依赖 `functional_dependency` | 模块／外部系统，依赖方 → 提供方；虚线、开放箭头 | 使用的业务能力                       |
| 模块关联 `module_association`    | 模块／外部系统；实线、无箭头                    | 明确的业务联系                       |
| 调用 `call`                      | 组件 → 组件；虚线、开放箭头                     | `动作（核心输入）：返回含义`         |
| 读取 `read`                      | 组件 → 数据对象；虚线、开放箭头                 | `读取动作（查询依据）：读取内容`     |
| 写入 `write`                     | 组件 → 数据对象；虚线、开放箭头                 | `动作（定位依据；修改内容）`         |
| 对象关联 `object_association`    | 数据对象之间；实线、无箭头                      | 关联字段及两端数量，解释业务含义     |
| 事件 `event`                     | 发布组件 → 订阅组件；点线、开放箭头             | `事件（核心载荷）`，保留实际事件标识 |

前两类至少一端为本项目模块。返回信息写在原调用线上。有返回值时说明调用方得到的业务结果。已确认没有返回值时记录这一事实，资料不足时保留为未知。

对象数量绑定真实端点，换向后保持对应，未知数量填 `null`。事件仅说明发布和订阅，可靠性以实际机制为准。

例如，取消入口请求核对本人预约资格并取得结果：`取消预约（预约标识、顾客标识）：取消结果`。顾客与预约通过 `Booking.customerId` 关联；若已确认每条预约属于一位顾客、顾客可有多条预约，则顾客端 `1`、预约端 `0..*`。

### 技术说明

标题用实际机制名，如状态机、事务边界、策略模式；正文说明机制解决的问题，原因融入问题说明。范围精确覆盖单个或全部实际成员，不同说明范围允许交叉，各自只含实际成员；圈选表示机制范围，目录表示代码归属。

## 5. 更新时间线

页面将一项需求称为「目标」，将目标下的推进记录称为「进展记录」。

阶段回顾后，读者应能理解当前目标及其重要变化。先核对已有需求、记录及业务全景，再整理本次材料。

### 确定需求边界

**需求是一项可独立实施并验收的项目目标。**

以一项完整结果为单位，判断两项内容能否**分别确定范围、分别决定实施、分别验收**：

| 情形                                         | 归属                 |
| -------------------------------------------- | -------------------- |
| 为同一结果补充字段、布局、异常情况或完成标准 | 更新同一需求正文     |
| 实现同一结果所需的前端、后端和数据库工作     | 同一需求中的实施内容 |
| 可单独决定实施并验收的另一项目目标           | 新建需求             |

标题直接说明目标。同一目标持续维护，后续可独立验收的改进另建需求，随项目推进逐步建立。

目标或归属不清时，保留现有对象身份，列明待确认项；继续整理已确认内容。

### 需求正文填写要求

需求字段的填写要求以需求内容 Schema 为准。

### 划分推进记录

**推进记录保存一项重要结论或结果，说明必要的原因、约束和影响，有且只有一个主需求。**

同一结论的背景、实施和验证可合写，独立结论分开记录；跨需求各记自身结论，可共用来源。聊天轮次、工具调用和代码提交仅提供整理材料。

正文采用自由 Markdown，建议 **100～200 字**。需求正文维护当前有效规则，记录保留建立或改变规则的重要决定。

### 区分修订和新进展

**修订用于更正或更新已有内容，保留原对象身份。**

| 情形                             | 处理方式                                               |
| -------------------------------- | ------------------------------------------------------ |
| 后来形成新决定或结果             | 新增记录；承接或改变旧决定时，引用其具体修订并说明变化 |
| 真实决定改变需求范围或行为       | 修订需求正文，并新增记录说明变化                       |
| 原内容误记、遗漏、时间或归类错误 | 修订原对象，保留身份和更正历史                         |
| 仅调整措辞、排版或修正错别字     | 修订原对象，通常无需新增推进记录                       |

### CoSeed 写法示例

假设进展记录只能在目标详情中阅读。开发者想了解几个目标的近期进展，需要逐项打开详情。

**需求正文示例**

> 开发者打开时间线时，可以看到每个目标最近两条进展记录的标题和摘要，按收录时间从新到旧排列。打开目标详情可以阅读全部记录。

**推进记录示例（确定近期记录预览方案）**

> 本次决定在时间线上为每个目标预览最近两条记录，以减少逐项打开详情的次数。完整记录保留在详情页。预览方案已定，待实现后验证。

### 确定状态

| 状态     | 成立条件                             |
| -------- | ------------------------------------ |
| 设计中   | 需求理解、UI／交互或技术方案仍在形成 |
| 方案已定 | 必要设计足以支撑实现                 |
| 待验收   | 完整实现尚待核对约定要求             |
| 已完成   | 已核对并满足完成标准                 |
| 暂缓     | 当前决定暂时停止推进                 |
| 取消     | 当前决定取消需求                     |

六种状态均可回退、恢复和跳转，依据实际进展选择。设计确定至完整实现确认期间可保持“方案已定”；“已完成”须有满足完成标准的验证依据。

## 6. 保留依据和未知

每项结论应有实际材料支持，并说明材料与变化的关系。代码和验证材料应对应明确代码状态；缺少聊天原文时可使用已取得的材料，并说明缺失。摘要、推断、原始证据分别标识，文档记录与可见用户原话分别核对。

更正保留对象身份、修改前后历史、操作者、时间和来源。人工更正与后续整理发生冲突时，保留现有内容，说明冲突并核对；资料不足处保持待确认。

## 7. 保存并核对结果

回顾完成后，一次保存能够共同成立的变化及其来源，以服务端回执确认结果。需要接着核对本次保存结果时，按回执中的项目版本读取。

向用户说明实际修改、依据、验证结果及未完成部分。业务代码状态和 CoSeed 资料状态分别记录；服务校验覆盖结构和引用等技术条件，真实性及业务完整性仍需阅读核对。
