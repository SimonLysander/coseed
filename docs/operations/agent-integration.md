# Agent 接入与使用指南

CoSeed 保存项目综述、需求演变和业务设计，帮助开发者理解项目并参与决策。本文说明协作流程和内容编写，页面与 `read_guide(topic="usage")` 共用全文；工具用途、参数及结果由 MCP 工具描述和 Schema 定义。

## 1. 明确任务

Agent 的任务是结合用户目标、项目资料、代码和验证结果，维护当前认识及其来源，使读者理解**结论、原因、边界和变化**。用户讨论支持意图与决定，代码支持当前实现，验证结果支持其条件内的行为；事实、推断和未知分别表述，影响业务判断的缺失或冲突需说明并确认。

**由用户明确发起阶段回顾或资料同步**，指定讨论及代码范围。一次回顾可涉及多个需求，一个需求可持续多次回顾。按重要结果维护内容：整体认识改变时更新综述，独立目标改变时维护需求，新决定或结果新增记录，原内容误记时修订，模块变化时更新受影响的设计。保留未受影响的内容，聊天轮次和工具调用只作为过程材料。

数据库保存权威内容及历史，Agent 通过 MCP 正式写入，客户端文件能力建立本地读取副本；业务仓库无需提交缓存、增设资料 Git 或连接器。业务代码的实现、验证和提交由开发者及其 Agent 完成。

### 内容表达规范

适用于本文及全部 Agent 正文；原始材料保留原文。

- **语体**：使用朴实、准确的书面语和明确术语；禁止口语俗词、拟人比喻和口号。
- **逻辑**：按理解顺序直接说明观点、原因和适用边界，段落按因果、条件或承接关系展开。禁止故意倒装逻辑；仅在确需澄清概念混淆时使用对举式、纠正式或反转式句型。
- **组织**：先确定逻辑结构，再选择格式。标题划分主题，段落连续解释，无序列表归纳并列项，有序列表表达步骤，表格比较同类信息，加粗关键结论，行内代码及代码块展示字段、路径和结构，引用块标明原文或示例，链接提供可核对的来源。各节按内容选用，无需使用全部形式。

## 2. 连接并读取项目

在 Agent 客户端添加 MCP 服务，默认地址为 `http://127.0.0.1:4310/mcp`，实际以启动输出为准。运行见[本地开发和运行](local-development.md)。当前仅本机可用，远程部署、认证和项目授权尚未实现。

选定项目后读取完整资料；新任务或恢复会话时核对版本。空项目结合代码、文档和用户背景首次整理，缺少历史时明确说明。

完整资料用于查找和核对，加入上下文的内容按当前任务选择。客户端下载、核验全部文件后再启用本地副本，失败时保留旧副本及其真实版本。缺少文件能力时说明尚未落盘，缓存可从权威内容重建。

## 3. 更新项目综述

综述表达**当前整体需求**，固定三部分；形成和变化过程由推进记录保留。

| 部分     | 编写要求                                                                                       |
| -------- | ---------------------------------------------------------------------------------------------- |
| 产品表述 | 说明产品是什么、为谁解决什么问题及已确认范围；自然 Markdown，可有小标题，正文必填              |
| 核心概念 | 解释理解业务所必需的概念，按业务语义选词；用词条和关系表达，数据库表作为实现依据               |
| 使用示例 | 开篇交代参与者、当前情况、共同前提和目的；每个小标题下先放对应用例图，再以自然段落讲清使用过程 |

概念关系：**种属** `kind-of` 为子类 → 父类，缩进仅表示种属；**组成** `composition` 为整体 → 部分；**关联** `association` 按 source → target 用具体名称说明联系。当前词条仍平铺，展示差异保留待核对。

用例图角色在系统外，用例在内，连线表示角色参与用户目标；先后由正文解释。每节图与正文引用一致，可复用角色和用例，整组仅保留各节图。独有前提写在该节，步骤编号按需使用。材料不足时概念、示例可留空，已有示例小节时必须提供开篇背景。

## 4. 整理需求推进

**需求**是可独立推进的用户目标，说明服务对象、问题、范围和完成标准。同一目标、主要范围和完成标准继续归入原需求；可单独决定开展、独立推进及验收的目标另建需求。身份跨聊天、日期和版本保留，管理字段使用已约定范围。

**记录**有且只有一个主需求，说明一项重要结论或结果及必要原因、约束和影响。自由 Markdown 通常约 **100～200 字**，为阅读建议；无关结果分开记录，同一结果涉及多个独立需求时各记自身结论，可共用来源。

| 情形                             | 处理方式                                               |
| -------------------------------- | ------------------------------------------------------ |
| 后来形成新决定或结果             | 新增记录；承接或改变旧决定时，引用其具体修订并说明变化 |
| 原记录误记、遗漏、时间或归类错误 | 修订原对象，保留身份和更正历史                         |
| 需求正文更正或更新               | 保存新修订，按实际结论判断是否新增记录                 |

> **虚构预约项目示例**：需求“顾客自主取消预约”的范围为本人尚未开始的预约，完成标准包括显示取消结果、拒绝取消他人或已开始的预约。
>
> 原记录误写为“所有预约”时应修订；后来真实决定扩大取消范围时，应新增记录并引用旧决定。示例仅说明写法。

实际发生时间依据材料填写，未知保留空值，更正也需依据。收录和保存时间由系统记录，时间线按首次收录顺序倒序，修订保留原位置；关联旧决定时保留当时的固定版本。

### 确定状态

| 状态     | 成立条件                             |
| -------- | ------------------------------------ |
| 设计中   | 需求理解、UI／交互或技术方案仍在形成 |
| 方案已定 | 必要设计足以支撑实现                 |
| 待验收   | 完整实现尚待核对约定要求             |
| 已完成   | 已核对并满足完成标准                 |
| 暂缓     | 当前决定暂时停止推进                 |
| 取消     | 当前决定取消需求                     |

六种状态均可回退、恢复和跳转，初始值依据事实选择。必要设计确定至完整实现确认期间可保持“方案已定”。完成报告及保存回执分别只证明其所述活动，状态需核对表中条件。

状态变化应说明原因：真实推进引用同一需求的具体记录修订，状态纠错引用原始材料。初次状态依据已知事实，正文修订不改变原状态变化时间，旧状态历史的依据继续保留。

## 5. 更新业务设计

项目全景展示模块、外部系统及职责关系；模块内部展示一个模块的组件、数据对象和协作。图表达完整结构，执行顺序需另有行为依据。

### 节点和范围

**一张图的所有节点必须正交完备**：同层职责明确、无重复划分，必要职责均有节点。先审查职责重叠和遗漏，完成审查后再补连线；完整性需结合业务审阅。

| 节点                       | 直接展示内容                                   |
| -------------------------- | ---------------------------------------------- |
| 业务模块 `module`          | 名称、职责，分 `core`／`support`               |
| 处理组件 `component`       | 名称、处理职责及业务效果，说明通常约 40～70 字 |
| 数据对象 `data_object`     | 名称、业务含义、TS 类型及字段行内注释          |
| 外部系统 `external_system` | 名称、协作职责                                 |

节点静态显示必要内容，类、方法及 CRUD 清单属于更细实现；当前不提供 Hover 详情、点击展开或第三层代码页面。数据对象写法如下，字段按实际材料确定：

```ts
type Booking = {
  id: string; // 预约标识
  customerId: string; // 所属顾客
  startsAt: string; // 开始时间，ISO 8601
  status: 'confirmed' | 'cancelled'; // 本例预约状态
};
```

本模块对象在边界内，接触的其他模块或外部系统对象在外，并保留实际归属。每个节点只选一个核心实现来源，按真实目录归组；有 `modules/` 从该段开始，否则用仓库相对目录，路径仅在区域标题单行显示。

### 连线

**每条线保留具体业务说明**，再补充下表信息：

| 类型                             | 两端、方向及线型                                | 补充内容                             |
| -------------------------------- | ----------------------------------------------- | ------------------------------------ |
| 功能依赖 `functional_dependency` | 模块／外部系统，依赖方 → 提供方；虚线、开放箭头 | 使用的业务能力                       |
| 模块关联 `module_association`    | 模块／外部系统；实线、无箭头                    | 明确的业务联系                       |
| 调用 `call`                      | 组件 → 组件；虚线、开放箭头                     | `动作（核心输入）：返回含义`         |
| 读取 `read`                      | 组件 → 数据对象；虚线、开放箭头                 | `读取动作（查询依据）：读取内容`     |
| 写入 `write`                     | 组件 → 数据对象；虚线、开放箭头                 | `动作（定位依据；修改内容）`         |
| 对象关联 `object_association`    | 数据对象之间；实线、无箭头                      | 关联字段及两端数量，解释业务含义     |
| 事件 `event`                     | 发布组件 → 订阅组件；点线、开放箭头             | `事件（核心载荷）`，保留实际事件标识 |

前两类至少一端为本项目模块。返回信息写在原调用线上：明确没有返回写“无返回”，未知写“返回待确认”。对象数量绑定真实端点，换向后保持对应，未知数量填 `null`；事件仅说明发布和订阅，可靠性以实际机制为准。

例如，取消入口请求核对本人预约资格并取得结果：`取消预约（预约标识、顾客标识）：取消结果`。顾客与预约通过 `Booking.customerId` 关联；若已确认每条预约属于一位顾客、顾客可有多条预约，则顾客端 `1`、预约端 `0..*`。

### 技术说明

标题用实际机制名，如状态机、事务边界、策略模式；正文说明机制解决的问题，原因融入问题说明。范围精确覆盖单个或全部实际成员，不同说明范围允许交叉，各自只含实际成员；圈选表示机制范围，目录表示代码归属。

## 6. 保留依据和未知

每项结论应有实际材料支持，并说明材料与变化的关系。代码和验证材料应对应明确代码状态；缺少聊天原文时可使用已取得的材料，并说明缺失。摘要、推断、原始证据分别标识，文档记录与可见用户原话分别核对。

更正保留对象身份、修改前后历史、操作者、时间和来源。人工更正与后续整理发生冲突时，保留现有内容，说明冲突并核对；资料不足处保持待确认。

## 7. 保存并核对结果

回顾完成后保存本次受影响的内容及来源，以实际回执确认结果，再同步本地资料。副本刷新失败时保留旧副本，仅补做下载。

向用户说明实际修改、依据、验证结果及未完成部分。业务代码状态和 CoSeed 资料状态分别记录；服务校验覆盖结构和引用等技术条件，真实性及业务完整性仍需阅读核对。

### 本版待核对

产品固定句式、概念粒度和解释长度、种属缩进与平铺差异、技术主题分类、失败草稿／自动运行／分批回顾，以及完整历史与早期原始确认继续待核对；节点正交完备按实际业务审查。
